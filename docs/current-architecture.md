# Current Architecture

This document describes the implemented pipeline. The ADRs under `docs/adr/` describe accepted design decisions and target architecture; their `implementation` metadata distinguishes current behavior from planned guarantees. Numbered releases in historical ADRs are roadmap milestones, not separate operating modes.

The [acceptance runbook](acceptance.md) records the required local and live proof. Implementation alone does not establish acceptance.

For a visual introduction, see the [workflow guide](workflows/README.md): the stage pipeline, finding decisions, and recovery/custody paths.

## Entry points

`orca-no-mistakes` supports these user-facing commands (plus the internal `gate` command used by the managed receive hook and the internal `report` command used by stage workers; each run hands its workers a copy of the program frozen under `artifacts/<run-id>/program-<nonce>/` so an edited or conflicted checkout cannot break report validation mid-run):

- `run` creates or reuses a deterministic direct admission. A newly pending admission launches the coordinator detached in an isolated child gate worktree and dedicated Orca terminal tab and returns `{"detached":true,"terminalHandle":"..."}`. An admission already being handled or accepted instead returns `{"admissionId":"...","replayed":true,"runId":"..."}` immediately without launching another coordinator; `runId` is `null` until a live launch binds its run, while a dead unbound launch is reclaimed first. If `--notify <handle>` is passed or `ORCA_TERMINAL_HANDLE` is set, the coordinator also notifies that terminal when a decision gate opens and notifies and wakes the originating session on terminal run outcomes (`passed`, `failed`, or `cancelled`); an outcome counts as delivered when either transport succeeds, and when no transport can deliver it the coordinator retains the gate worktree, branch, terminal, and marker for later `prune --stranded` recovery instead of cleaning them up. The internal `--attached` flag runs synchronously inside the spawned terminal tab; unless `--no-tui` is passed, the detached launcher injects `--tui` so the attached coordinator renders the interactive Run TUI by default, falling back to plain status on terminals that do not support it, while `--no-tui` renders each newly committed presentation snapshot as one bounded semantic stderr line and leaves stdout for the final structured result.
- `init` idempotently installs a repository-scoped bare gate at `<git-common-dir>/orca-no-mistakes/gate.git`, pins its own hooks path, advertises push options, and wires the managed `orca-no-mistakes` remote; verifying GitHub authentication and route persistence occur only for a GitHub upstream, while provider-neutral init installs the local gate without a publication route. Its `pre-receive` path accepts exactly one non-delete feature-ref update plus one canonical `no-mistakes.intent=<base64url>` option, validates the proposed commit in Git's quarantine, records or reuses a deterministic admission in the repository ledger, and launches a detached coordinator with receive state and pipes removed from its environment. The coordinator waits for the exact permanent ref, anchors that OID under `refs/orca-no-mistakes/heads/<run-id>` with a Git CAS transaction, and launches the existing isolated gate-worktree pipeline. During pipeline initialization, the domain run is created and bound to the admission, the branch lease is acquired, recovery context is registered, and only then is the admission marked accepted. Direct `run` admissions use the same ledger boundary and identity. A same-head push with no unfinished matching admission is a no-event, while a matching pending or launched admission is consulted and re-engaged; a same-head accepted admission is also a no-event, but an accepted admission that reaches the admission replay path returns its bound run.
- `attestation export|verify` writes a portable completion attestation manifest (`version: "2.0.0"`), or checks one against its own digests and — when this ledger holds the run — against the stored record and retained evidence. Both commands accept `--repo <path>` to name the repository ledger; without it they use the current directory. Explicit `--repo` fails closed if the repository cannot be resolved. See [Retained run compatibility](#retained-run-compatibility) for historical data handling.
- `prune [--before <date>] [--repo <path>]` deletes completed runs (cascading checkpoints, evidence, gate audit rows, attestations, and the run's frozen plan and immutable facts) plus their artifact directories; `prune --stranded [--repo <path>]` instead reaps dead gate and direct-run resources and rejects `--before`. `--repo` selects every run whose recorded root is that path or nested under it. The ledger row is deleted before its artifacts, because the delete re-checks the lease and can refuse a run that was leased again since selection; a failed removal therefore orphans a directory rather than stripping the evidence of a run that survived. It never deletes refs: preserved commits outlive the pruned run. Nothing else deletes evidence: there is no TTL or count-based eviction. For `prune` without `--stranded`, a run is retained when it still holds a branch lease, when its repository root is unavailable and `--repo` does not name that exact root (the exact-root assertion applies only to this case), or when any of its recovery refs — `refs/no-mistakes/recover/<run-id>`, the `-fixer-<stage>-<round>` children anchored per fixer round, and `refs/no-mistakes/recover-generations/<run-id>/<generation>` — is not an ancestor of its branch, base, or `origin/<base>`. A generation ref preserves the prior resume generation's tip, so it retains a completed run until that commit merges; the run becomes prune-eligible after containment is proven. A container ref that no longer resolves, such as a feature branch deleted after its merge, is skipped rather than treated as an inspection failure; any other Git failure aborts the prune instead of deleting evidence on a guess. Containment is proven outside the delete transaction and is not fenced against a concurrent run rewriting the same branch: because prune never deletes refs, the commits of a run pruned in that window stay reachable at their recovery ref, and only its row and logs are lost.
- `evaluation <seed|capture|list|replay|adjudicate|compare|prune>` captures fixed review cases and replays the review worker against them to compare findings with adjudicated labels. It is review-only: it needs no Orca run and no GitHub publication initialization, and it never publishes. [Review evaluation](review-evaluation.md) is the authoritative workflow documentation.

Before deleting a completed run, `prune` deletes every `submission_admissions` row bound to it. An identical later submission is therefore admitted again instead of replaying the pruned run.

Stranded recovery also handles direct attached Force stops. Their marker records the exact HEAD and owned worker state; recovery preserves that commit, reaps those workers, atomically settles an in-progress run cancelled and releases its lease, then removes only the marker, never the operator checkout or branch. If the run already reached `passed` or `failed`, recovery verifies the recorded commit is already preserved and leaves that terminal status unchanged.

New runs require an explicit single-line `--intent`; `--resume <run-id>` instead reopens a failed run with its stored intent. The runner requires a clean, committed, named feature branch, rejects the detected default branch, verifies an `origin` remote, and optionally checks an expected `--head` SHA. It fetches and rebases onto the selected base before validation continues.

## Domain ledger

Each repository's identity and provenance state lives in SQLite at `<git-common-dir>/orca-no-mistakes/ledger.sqlite` (WAL mode, foreign keys on), created via `node:sqlite`. Every run freezes its stage plan (position, stage id, requirement) into `stage_plan_entries` in the same transaction as its `runs` row.

The twelve immutable fact tables — `stage_plan_entries`, `stage_dispositions`, `stage_disposition_supersessions`, `publication_routes`, `publication_baselines`, `run_attempts`, `attempt_outcomes`, `remote_observations`, `mutation_intents`, `resolved_mutation_intents`, `remote_receipts`, `auto_fix_mode_events` — are write-once: UPDATEs abort unconditionally, and DELETEs abort while the run's own row still exists, so those rows leave only through the cascade when `prune` deletes the run. The default flow populates the frozen plan, stage dispositions and supersessions, route and baseline, mutation intents, authoritative remote observations, both remote receipts, Auto-fix mode events, and per-attempt custody facts. Twenty-eight tables:

- `runs` — one row per run with submission commit OID, base branch/OID, intent + intent hash, trusted-policy hash, and terminal status (`in-progress`, `passed`, `failed`, `cancelled`); resumed attempts reuse the same row (`run_attempts` holds one row per attempt).
- `submission_admissions` — one deterministic submission identity per direct or gate ingress, carrying repository/ref/OID/intent identity, lifecycle status, optional launcher PID, and later run and accepted-OID binding. An accepted binding persists until its run is pruned; removing both allows an identical later submission to be admitted again.
- `pending_admission_leases` — one exclusive unfinished-admission lease per repository ref, preventing competing pending or launched submissions until acceptance, failure, or supersession releases it.
- `repository_migrations`, `repository_migration_imports` — import markers for [retained historical data](#retained-run-compatibility).
- `repository_publication_routes` — the durable, repository-scoped publication route: one mutable row per repository keyed by the canonical Git common dir (shared by every worktree), holding the forge host, stable repository/node/fork-network-root identifiers, owner and branch coordinates, the authenticated actor identity, its credential source (a label, never a secret), and the backend identity. Unlike the write-once per-run facts it does not belong to a run: it is upserted in place and refuses a repository-identity change while in-progress runs or resumable failed runs (failed runs whose latest attempt outcome is resume-eligible) still depend on the stored route. New CLI runs snapshot it at start, with their own head and base branches, into an immutable per-run `publication_routes` fact.
- `stage_plan_entries` — the run's frozen stage plan, one row per stage with position, stage id, and requirement (`required`, `optional`, `disabled`); new CLI runs freeze the nine required core stages plus one required entry per configured command gate (see [Repository command gates](#repository-command-gates)). Resume preserves the stored plan.
- `stage_dispositions` — the initial terminal disposition per plan stage (`satisfied`, `failed`, `skipped`, `waived`, `disabled`), bound to its plan entry and optionally to an evidence digest.
- `stage_disposition_supersessions` — immutable history of stage disposition supersessions when a satisfied stage is re-evaluated or revalidated under new evidence, linking the stage and its updated disposition to both the prior and new evidence digests.
- `publication_routes`, `publication_baselines` — a run's route fingerprint with forge host and owner/branch coordinates, and its authoritative head-commit baseline (including the proven absence of one) bound to the canonical credential-free head-repository identity used at admission.
- `run_attempts`, `attempt_outcomes` — per-attempt custody facts populated by the default flow as well as focused publication: which coordinator/actor identity started each attempt under which generation token, and its terminal outcome (verdict, stopping fact, reason, candidate commit, custody and receipt digests, resume eligibility) stored with a SHA-256 digest over its canonical JSON.
- `remote_observations`, `mutation_intents`, `resolved_mutation_intents`, `remote_receipts` — hash-bound observations of remote state, intended remote mutations (candidate publication and pull-request report publication), durable mutation intent resolutions recording definite-failure, lease-lost, or authoritatively reconciled outcomes, and the resulting receipts bound to the authoritative post-observation.
- `auto_fix_mode_events` — the run's immutable Auto-fix mode history: one append-only row per mode change with the enabled flag, source (`initial` at run creation from `auto_fix.enabled`, or `operator` for a Run TUI toggle), and timestamp; resume restores the durable pipeline mode for the run, while the Run TUI restores its local auto-responder switch only from an operator-sourced mode event.
- `branch_leases` — one exclusive semantic lease per `(repo_root, branch)` with a monotonically increasing generation token and heartbeat timestamp. A second run on a leased branch fails closed; `--force-lease` reclaims it. The lease heartbeat is checked before every stage and each fix round; losing the lease aborts the run. The lease is released when the run passes or fails.
- `lease_generations` — per-repository counter minting the monotonically increasing lease generation tokens.
- `resume_claims` — one claim per resumed run binding the run to its resume generation token.
- `stage_checkpoints` — every completed stage and fixer round records its input and output commit OIDs (each fixer must commit a distinct change). Detached resume reconstructs the isolated gate worktree at the newest checkpoint output while the initiating checkout remains at the original submission commit for automatic custody transfer. When a resumed generation rewrites lineage, `refs/no-mistakes/recover-generations/<run-id>/<generation>` preserves the previous generation's tip.
- `stage_evidence` — one row per stage execution binding stage id, round, candidate/base commit OIDs, worker identity, exit code, summary, findings, artifact path, the SHA-256 artifact digest, and the SHA-256 evidence digest. Indexed by run and by `(run, stage, round)`.
- `gate_audit` — every stage-scoped decision gate, including CI and guardrail recovery (worker-question relay and durable resume gates are excluded; see [Findings and gates](#findings-and-gates)), written when the gate opens with its kind (`exhaustion`, `finding`, or `guardrail`; CI is a stage, not a separate kind) and updated on resolution with the raw resolution, parsed decision, guidance, and selected finding IDs. Approve, skip, and stop store an explicit empty ID array, while an unresolved or invalid resolution keeps the field null. An unresolved gate stays `pending` with a null `resolved_at`.
- `media_publications` — one row per media publication attempt, keyed by run, candidate commit OID, artifact SHA-256, forge repository identifier, and host, with the initial artifact path, status (`pending`, `published`, `failed`, `uncertain`), attachment URL, and detail. The row is inserted `pending` only while the coordinator holds the branch lease, so each key is attempted at most once, and settles in place; see the publication contract in [Orchestration](#orchestration).
- `media_publication_artifacts` — canonical artifact paths associated with each publication identity. Reservation records each validated path under the branch lease; lookup requires that same path. Distinct paths with identical bytes retain separate associations while sharing the upload outcome. Existing ledgers acquire associations when their artifacts are revalidated on publication or refresh.
- `presentation_snapshots` — append-only immutable projections of run attempts, mode, stage, round, distinct reviewer analysis ordinals, finding counts by disposition, retained fix summaries, durable fixer completion and blocker states, gates, errors, cancellation, and terminal outcomes. Settlement, checkpoint, and passed-terminal snapshots commit in the same transaction as their domain milestones; finding and gate snapshots follow their durable ledger rows, while start, round, reviewer findings, fixer-completion, and fixer-blocked transitions are durable presentation events themselves. Resume loads the latest projection to continue presentation state while reconstructing the interactive rail activity history from persisted snapshots without re-emitting plain-status output. Transient elapsed time, cursor state, pane state, activity previews, and raw worker output are never stored.
- `passed_attestations` — one row per passed run keyed by run ID, holding the manifest JSON and Merkle root; lookups by candidate commit OID return the most recent attestation.

Set `ORCA_NO_MISTAKES_HOME` to relocate artifacts (used by tests and sandboxes). It does not relocate repository ledgers.

## Orchestration

The coordinator creates one Orca Run and an ordered DAG of the nine core tasks, extended by one task per configured command gate (see [Repository command gates](#repository-command-gates)):

`intent -> rebase -> review -> test -> document -> lint -> push -> pr -> ci`

A detached `--resume` creates a new Orca orchestration run for only the remaining suffix of its stage plan while retaining the original domain run ID, artifact directory, evidence history, and attestation identity. Detached launch reconstructs the isolated gate worktree at the selected durable checkpoint and leaves the clean initiating checkout at the original submission commit so successful custody transfer can advance it automatically. The coordinator atomically reopens the failed ledger row and reacquires its branch lease, restores prior evidence and resolved approvals, replays a recorded `fix` decision that was interrupted before its fixer ran, and starts at the first incomplete stage. Commit-bound validation evidence is rerun when its candidate no longer matches the checkpoint HEAD.

The Run TUI adds a same-process resume path distinct from detached `--resume`. When a failed attempt settles with at least one checkpoint and its error is a resumable stage execution failure (including the remote stages) — excluding setup, rebase, worker-cleanup, gate-stop, and post-mutation custody failures — the coordinator first drains the attempt's registered workers, then settles the failed attempt with its outcome and waits for the operator. A detached coordinator opens a durable Orca orchestration gate with `resume` and `stop` resolutions and wakes the originating terminal with the exact `orca orchestration send` response command; agents use that command rather than injecting terminal input. A human focused on the coordinator TUI may still press `R` or `C`, and the coordinator records that choice by resolving the same gate. If neither notification transport succeeds, it leaves the run stopped instead of waiting invisibly. Resume reacquires the resume claim and branch lease under a new generation token, starts a new attempt under the same domain run and the same Orca orchestration run, and continues from the durable checkpoint; stop leaves the run stopped for a later detached `--resume`. A setup failure of the resumed attempt fails closed: the run settles failed with the resume claim cleared. When the interactive renderer is unavailable (plain-status fallback), the resumable error simply stops the run instead of waiting, and a renderer failure while that wait is open revokes it — the run settles failed with its original error — so detached `--resume` remains the recovery path in both cases.

`intent` records the supplied objective behind `<untrusted_instruction>` framing. `rebase`, `push`, `ci`, and every `command-<name>` gate are coordinator-run operations; the other stages run worker evaluations returning structured reports. `push` publishes the exact validated candidate under a durable force-with-lease baseline and post-read. `pr` runs a drafting reviewer through `executeStage` to draft a conventional title and branch-wide change summary from the final diff, then assembles a bounded report under a 63,488-byte budget (truncating oversized intent or What Changed sections with `_[truncated to fit GitHub PR body limits]_` when necessary) deterministically appending the run intent, colon-formatted risk, testing commands and descriptively labeled artifacts, and pipeline attestation. Under the safe-publication contract, retained artifact bytes are withheld by default while name, SHA-256 digest, and size are published. Text artifacts are embedded as previews only when the exact candidate-bound digest is trusted, after secret redaction and a 16 KiB preview cap. Media artifacts take a separate opt-in path that publishes the entire approved binary snapshot unredacted, because binary bytes cannot be secret-redacted. Media publication requires `media_publication.enabled` plus the artifact's exact SHA-256 in `media_publication.approved_sha256` (the validation-policy section below owns how those approvals merge and when they are trusted), requires the artifact's evidence candidate to equal the published candidate, and requires a nonempty singly-linked regular file inside the evidence root, reached without symlinks, whose magic bytes match one of PNG, JPEG, GIF, or WebP (up to 10 MiB) or MP4, QuickTime, or WebM (up to 100 MiB); any other extension, an unmatched digest, or a file that changes during validation stays digest-only text. Uploads target `github.com` only with an OAuth or personal-access token, so GitHub Enterprise Server hosts and App/Actions credentials are rejected. A published image renders in the report as an attachment image and a published recording as an attachment link. Each attempt is durably bound to the run, candidate, digest, repository ID, and host under the current branch lease and settles `pending` into `published`, `failed`, or `uncertain`; the local evidence is retained in every outcome, an uncertain or failed attempt is reported as not confirmed viewable, and a recorded attempt is never retried automatically — retrying requires a new run after investigating the previous attempt. Reusing a retained PR body rechecks every already-published digest against the current approvals and fails the stage when one is no longer enabled or approved. The report turns authoritative reviewer rounds and retained fixer summaries into semantic finding → fix → re-check folds, records approved/skipped outcomes without calling them successful, and includes running PR plus pending CI states in the machine-readable lifecycle snapshot. It creates or updates the original non-draft PR body for the exact stable repository/ref/candidate tuple. After the authoritative body/title post-read, the coordinator notifies and wakes the originating terminal with the PR URL and settles the stage immediately with an open pull-request binding receipt (`state: 'open'`, title and body hashes, pipeline evidence root). `pr` no longer awaits merge.

`ci` is coordinator-owned like `push` (no worker agent) and runs CI monitoring until the pull request leaves the open state. Each tick observes the exact PR by route and candidate head — title, body, head, and draft state must still match the `pr` receipt, otherwise the stage throws `pull-request facts changed while monitoring CI` — then reads the PR state, mergeability, and the head commit's check rollup bucketed as pass, fail, pending, cancel, or skip. ADR-0016 owns the decision table (merge upgrades the pull-request binding receipt to `state: 'merged'`, close fails the stage, failed or cancelled checks and merge conflicts open a gate once nothing is pending, everything else keeps polling), the poll pacing, and the idle timeout. The `ci` gate offers `fix` and `stop`: `fix` resumes monitoring after the human has acted externally (reran checks, resolved conflicts, or merged); the stage performs no automatic repair.

Publication binds the canonical credential-free head-repository identity and authoritative fully qualified head-ref baseline; equivalent HTTPS and SSH spellings remain usable only when mandatory stable repository ID and node ID resolution identifies that same stored repository. It rejects Git URL rewrite configuration, requires the current generation-fenced branch lease, verifies each satisfied local stage's retained evidence artifact, and requires a contiguous terminal checkpoint chain. It then either records a no-op, reconciles an already-present exact candidate, or runs `git push --porcelain` with an explicit fully qualified refspec and `--force-with-lease=<ref>:<expected>`. Every attempted write is followed by an authoritative post-read and another stable repository identity check; only exact remote facts atomically settle the receipt, evidence, disposition, and checkpoint.

Gate, CLI-worker, and ACP-worker creation explicitly reasserts the parent relationship after Orca returns the creation receipt, so an intermittently dropped create-time lineage record does not leave controllers or workers detached in the workspace hierarchy.

Reviewers run as fresh workers in disposable child worktrees. A compatible fixer terminal and child worktree are retained across fix rounds, with each committed repair applied back to the coordinator's isolated gate worktree; changing the primary configured fixer, observing that its worktree no longer matches the pre-round head, finding uncommitted changes, or failing to acknowledge retained-worker completion releases it before launching a fresh session. Another round enters through Orca's supervised `worker-start --terminal` path, which verifies that a recognized agent process still owns the terminal before delivering the authenticated task; a terminal that returned to its shell is released and retried through the fresh configured chain even when its stale title still names the old harness. If a retained terminal fails before accepting another round, the coordinator releases it and retries the full configured chain in fresh child worktrees. Retained fixers are released before an ordinary finding or exhaustion gate opens; a strict-mode content rejection instead keeps the worker retained at the recovery gate described in the guardrail contract below. Every successful fixer round must leave a clean worktree and create a new commit. A fixer that reports no applicable change is cleaned up, recorded as evidence, and routed to the human gate so the operator can approve or skip a false finding or explicitly retry it.

The new commit must also change the pre-round tree. Empty commits are treated as no-change outcomes and follow the same cleanup, evidence, and human-gate path.

Fixer prompts restrict edits to implementation source and new regression tests (or the narrower document-stage scope). The coordinator binds policy inspection, custody transfer, and post-transfer HEAD verification to the same exact fixer commit OID, rejecting a worker or concurrent writer that substitutes a later commit after validation. Ordinary fixer commits must descend from the pre-round head. Rebase conflicts are never agent-fixed: the coordinator records the exact upstream OID from the same fetch/rebase attempt, pauses with only `fix` (retry after human resolution) or `stop`, and reruns the rebase stage when requested. In `strict` guardrail mode it rejects changes to tests present at the pre-round head, validation command/configuration files (including test-runner selection), and its executable entrypoint before applying a fixer commit. In the default `advisory` guardrail mode, protected-path and assertion changes proceed to custody while being recorded as guardrail violations, followed by fresh review. Explicit trusted-base `auto_fix.guardrails: strict` opts into content rejection. Branch ownership, unauthorized writes, history rewriting, and publication identity remain hard boundaries in both modes. Coordinator source that entrypoint imports is code under review and stays fixable. Documentation under `docs/prompts/` remains ordinary document-stage content. A protected-content commit rejected in `strict` mode is anchored and retained in its worker worktree at an indefinite human recovery gate showing the exact commit and warnings. `approve` transfers that exact candidate under the normal custody checks and reruns review; it does not waive review findings. `fix` discards the worker and returns to the original findings gate for retry; `stop` ends the run. Custody after approval receives a fresh worker-attempt timeout. Recovery is available in the active coordinator; restarting during this gate does not automatically adopt the rejected candidate.

This deliberately includes mechanical test/lint edits to an existing test file because the coordinator cannot prove that a file-level rewrite preserved its assertions. The path-level guard covers dedicated test files, including Perl `t/*.t`, Terraform `*.tftest.hcl`, Gherkin `features/*.feature` plus conventional `features/support/**` and `features/environment.py` support code at any repository depth, Bats `*.bats`, `specs/` and `__specs__/` directories, prefix-style `testFoo` and `TestFoo` names, C++ `*_unittest` files, snapshot assertions under `__snapshots__/` or `*.snap`, fixture/golden data under conventional `testdata`, `fixtures`, `__fixtures__`, or `golden` directories, Cypress/Playwright-style `*.cy.*` and `*.e2e.*` files, and pytest `conftest.py`. For ordinary implementation paths, the coordinator compares committed blob contents directly, independent of Git attributes and textconv. Any change to a pre-round source file containing a direct/chained test registration or an assertion-framework import anywhere in the source is detected as a content change, covering control-flow-prefixed registrations and chained skip/only changes without language-specific parsing; documentation extensions (`.adoc`, `.md`, `.mdx`, `.rst`) are exempt from this whole-file freeze and instead receive the same statement-level assertion-unit and skip-marker protection as a merely-asserting file. A file that merely asserts is inspected at statement level instead: each assertion, together with its multiline continuations or its doctest expected output, is compared for alteration, so unrelated edits to the same file never register as content changes. Whether a detected content change is recorded as an advisory warning, rejected, or accepted at the strict recovery gate follows the guardrail mode and recovery contract described above. Any changed pre-round path referenced by a protected manifest, CI workflow, or runner/build configuration is also protected; references resolve from both the repository root and the referring manifest's directory. A referenced local action protects its complete tracked implementation tree, while unreferenced files with similar names remain editable. Custody updates the operator worktree only while detached and moves its named branch through an exact compare-and-swap, preserving concurrent branch advances. A timeout before or during custody transfer restores the pre-round head; once transfer finishes within the deadline, coordinator verification and cleanup finish under their normal command bounds. Final certification remains fail-closed until the retained fixer terminal and worktree are released.

Validation references normalize optional trailing directory separators and resolve each CI step's `working-directory` or a shell command's `cd` together with that same command path, including newline-separated shell blocks, so separate steps cannot cross-match unrelated files with the same basename. Non-YAML policy sources such as Jenkinsfiles are inspected as complete shell blocks so directory context survives intervening setup commands. Referenced local actions protect nested action implementations throughout every enclosing action tree. A workflow `uses: ./` protects the root action manifest and descendants of directory entrypoints referenced by that manifest, without turning unrelated repository paths into policy. Implicit Bazel and Gradle policy files such as `.bazelrc` and `gradle.properties`, plus Gradle and Maven wrapper scripts, properties, and implementation files, are protected without requiring textual references.

A successful fallback fixer remains compatible while the exact configured candidate chain and order stay unchanged. Common GitHub, Forgejo, GitLab, CircleCI, Jenkins, Azure Pipelines, Buildkite, Bitbucket, Travis, and AppVeyor CI configuration, complete local GitHub/Forgejo action implementation trees, CMake and Bazel build/test entrypoints including `CMakePresets.json` and `CMakeUserPresets.json`, Meson's implicit `meson.build`, `meson.options`, and `meson_options.txt`, Maven and Gradle build policy including `.mvn/maven.config` and `settings.gradle(.kts)`, Go module/workspace manifests, PHPUnit runner configuration, TSLint configuration, dependency lockfiles, and any `conftest.py` are protected validation policy and produce content guardrail warnings (or rejection in strict mode).

Clojure's canonical `project.clj`, `deps.edn`, and `build.boot` manifests are protected implicit validation policy. Validation-entrypoint closure also includes newly added paths when protected pre-round policy already names them, so a fixer cannot satisfy a missing check with a passing no-op.

Dedicated test-path protection also recognizes `.Tests`, `.UnitTests`, and `.IntegrationTests` project directories, hyphenated `foo-test` and non-document `test-foo` names, and Pascal/camel-case `Test(s)` or `Spec(s)` filename suffixes. While a human gate is open, the coordinator inspects and acknowledges the complete Orca delivery, applying authenticated gate responses and warning about unrelated messages rather than blocking or discarding the batch silently.

Every rebase attempt records the upstream OID fetched by that attempt, including conflicts, hook failures, and failures without unmerged paths; only a clean rebase updates the accepted run base. Exact `snapshots/` and Jest `__mocks__/` directories are protected test data. npm's implicit `.npmrc`, Go Task's `Taskfile.yml`/`Taskfile.yaml` and `Taskfile.dist.yml`/`Taskfile.dist.yaml`, `GNUmakefile`, and `.justfile` are protected validation policy. Validation references recognize repository-root command substitutions such as `$(pwd)` and `$(git rev-parse --show-toplevel)`, POSIX environment variables, PowerShell `$env:NAME`, Windows cmd `%NAME%`, and workflow-expression prefixes.

Each stage and role resolves its own agent from the configuration tiers, and the launch adapter dispatches on the resolved harness:

- `cursor` launches through native `orca orchestration worker-start`, which receives the resolved model, effort, and timeout as flags. Fresh Claude, Codex, Antigravity, and Kimi workers create their authenticated dispatch first, then launch through a local terminal with a protected mode-0600 preamble artifact. Claude, Codex, and Antigravity receive a short artifact instruction at launch. Kimi starts its interactive TUI with managed `--auto`, waits for stable readiness, and then receives the artifact instruction through Orca's agent-prompt terminal transport. Immediate argument, authentication, terminal, or readiness failures remain preflight failures. Retained CLI sessions re-enter through supervised `worker-start --terminal`, which validates agent ownership and delivers the authenticated task. Codex reasoning effort maps to `model_reasoning_effort` and automation uses `--dangerously-bypass-approvals-and-sandbox`. This avoids native fresh-launch prompt stalls, empty initial TUIs, prompt-processing races, one-shot Kimi execution, and OS argument-size limits.
- Before a fresh Kimi TUI starts, the coordinator refuses worktrees containing project `.mcp.json` or `.kimi-code/mcp.json`, then writes Kimi's exact per-workspace trust record only for that worker path. The temporary record is removed immediately after readiness and authenticated task delivery, so every fresh launch rechecks the worktree and automatic trust cannot enable branch-controlled project MCP servers.

## Validation policy

Two provenance rules bind every run. First, repository agent configuration is read from `.orca/no-mistakes.yaml` on the trusted base ref (`git show origin/<base>:.orca/no-mistakes.yaml`); an absent file resolves to an empty policy, and an unresolvable base ref fails the run. Second, the coordinator hashes its own script files as they exist at `origin/<base>` and records that digest in the ledger and attestation. Reviewer prompts frame repository content, diffs, and instructions as untrusted data; policy changes may only come from the coordinator prompt itself.

The extracted configuration supplies per-stage and per-role agent selection and is merged under the CLI flags. `--allow-local-config` reads the same path from the working tree instead, and `--config <path>` reads an explicit file that must exist. Either bypass marks the run uncertified: the Orca worktree status is prefixed `[uncertified: local config bypass]` and the artifacts manifest records `local_bypass`.

Media-publication settings are the documented exception to the scalar array replacement rule in [ADR-0011](adr/0011-hierarchical-configuration-and-precedence.md). `media_publication.enabled` uses repository-over-user precedence and defaults to `false`, while `media_publication.approved_sha256` is the deduplicated union of the user-global and trusted-repository approval lists; an empty repository approval list therefore does not revoke a user-global digest approval. Because `no_ci` and media approvals are trusted only from the base ref, either local-policy bypass strips the repository configuration's entire `media_publication` section and forces `ci.no_ci` back to `false`, leaving user-global approvals as the only ones still in effect.

## Findings and gates

### Repository command gates

Trusted-base `.orca/no-mistakes.yaml` may declare `command_gates` (default `[]`),
each with a unique `name`, an `after` anchor, and a nonempty `command`. Names use
lowercase letters/digits separated by inner hyphens, have at most 40 characters,
and cannot equal a core stage. At most 16 gates are allowed. Anchors are `rebase`,
`review`, `test`, `document`, and `lint`; declaration order is preserved within
each anchor. Gates appear as `command-<name>` in the existing stage plan, logs,
evidence, and reports, before publication. User-global and local-bypass
configuration cannot declare them. All command gates are required; optional,
skip, and agent configuration fields are rejected.

The run stores its declarations atomically with its frozen stage plan. Resume
uses that list rather than adding, removing, or retargeting gates from later
configuration; existing compatibility checks on other policy and base evidence
still apply. Commands execute under `/bin/sh` in fresh detached Git worktrees at
the exact candidate, with no implicit dependency installation. A command inherits
the coordinator's own environment — its `PATH`, toolchain, and any integration
credentials the caller exported — minus the Git repository, configuration, and
push-transport variables (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_CONFIG*`,
`GIT_PUSH_OPTION_*`, and related) that `cleanGitEnvironment` strips so the
command binds to its own worktree. There is no environment allowlist. Combined output
is retained up to 64 KiB with an explicit truncation marker, together with the
exit status and commit-bound evidence. POSIX process groups are killed when the
shell exits or the attempt is cancelled, then the worktree is removed. There is
no command or whole-run deadline. Deliberately detached processes are outside
this process-group cleanup contract; it is not a sandbox.

A nonzero exit opens `fix`/`stop`, even with auto-fix enabled. `fix` authorizes the
existing fixer and guardrail path using the anchor's fixer configuration, then
reruns the command on the repaired candidate. Approval cannot certify a failed
command. Candidate changes require fresh command evidence before publication.
Trusting the declaration does **not** freeze a branch-owned script it invokes:
the script executes from the candidate. Review changes to such scripts through
the existing unexplained-policy-relaxation review and fixer guardrails rather
than treating the declaration as immutable validation code.

Fixer labels are bound to the reviewer analysis that produced their findings, not to the internal evidence round. The first attempt after `Review analysis 3` is `Review fix 3`; a blocked retry is `Review fix 3 retry 1`. This identity is stored in presentation snapshots and reused by activity, detail, log, gate, and resumed TUI displays. Plain-status output uses it only for fixer start, completion, and blocker lines; its findings-recorded, gate-opened, and gate-resolved lines still print the internal evidence round.

When a settled local stage reruns on a changed candidate, a durable `stage-reopened` transition clears candidate-bound finding dispositions before analysis. New local settlements explicitly name the prior evidence they replace and append to `stage_disposition_supersessions`; the original settlement and evidence remain immutable. Effective disposition reads use the latest supersession, and settlement events distinguish newly reviewed evidence even when the internal round and candidate are unchanged.

Findings are `auto-fix`, `ask-user`, or `no-op`; a report finding that omits `action` defaults to `no-op` when paired with legacy `severity: "no-op"` (normalizing to `severity: "info"`), and otherwise conservatively defaults to `ask-user` instead of failing the report, while an explicitly invalid action still fails it. Reports containing only actionable `auto-fix` findings enter the fix loop automatically only while the run's durable Auto-fix mode is enabled; with the mode disabled they open the finding gate instead. Durable Auto-fix mode is recorded at run creation from `auto_fix.enabled` (with source `initial`), and every operator toggle from the Run TUI (`A`) appends an immutable `auto_fix_mode_events` row (with source `operator`); at the coordinator level a toggle affects only findings recorded after the change, and a resumed attempt inherits the latest recorded durable mode. Distinct from durable pipeline auto-fix, the Run TUI (`RailTuiRenderer`) maintains a renderer-local gate auto-responder switch. The TUI auto-responder always starts disabled even when initial durable pipeline auto-fix is enabled, restores that switch on resume only from an operator-sourced mode event (ignoring `initial` events), and when enabled by the operator immediately attempts to resolve the currently open decision gate (submitting `fix` when actionable findings exist and `fix` is offered, or `approve` otherwise). Some gates are exceptions the responder never resolves regardless of its state. Test gates whose recorded live-validation verdict is `inconclusive` or `no-surface` are left open for an explicit human decision (see the verdict contract in [README.md#live-test-evidence](../README.md#live-test-evidence)). Command gate decisions are also excluded, because a failed required command always waits for an explicit human decision (see [Repository command gates](#repository-command-gates)). Strict-mode guardrail recovery gates are excluded as well, and the TUI presents their candidate-level `approve`, `fix`, and `stop` choices (see the recovery contract in the content-guardrail section) instead of the per-finding editor, so a retained candidate always waits for an explicit human decision. Automatic repair through the responder is limited to at most one automatic `fix` per stage per attempt; any subsequent actionable gate for that stage is left open for human decision until the next attempt resets stage tracking. Each recorded finding carries a `fixed`, `approved`, or `open` disposition, surfaced as per-finding counts by both renderers, and resume reconciles approved stages back into the presentation. STAGES and ACTIVITY maintain distinct, complementary count and lifecycle semantics: STAGES rail summaries display stage-wide cumulative totals (total found, fixed, and approved counts, using open counts only for warning coloration), while the selected-stage detail panel presents explicit open, fixed, and approved counts, preserving approved findings across re-analysis rounds (`inheritApproval`). ACTIVITY records chronological per-cycle events: reviewer analysis rows report found counts derived from reconciled open findings (rendered as `0 found` when zero open findings remain); fixer completion first records targeted occurrences as provisional fixes applied with retained fixer summaries; and subsequent reviewer analysis replaces that provisional applied result with verified counts ordered as fixed, still open, and approved without displaying applied and fixed together. ACTIVITY counts are strictly per-cycle (accounting only for findings targeted, verified, or newly left unselected during that cycle) rather than stage-wide cumulative totals, preventing earlier approvals from being misattributed to later fixer retries. Duplicate finding IDs are accounted for by occurrence to maintain exact duplicate-safe accounting across cycles. When a fixer attempt produces no committed changes, or a policy violation propagates as an error (path-level violations, and strict content rejections after recovery is declined or unavailable; see the guardrail contract above, under which advisory violations and approved candidates continue instead), the coordinator synthesizes a blocking finding (`fixer-no-change` or `fixer-policy-violation` with action `ask-user` and `severity: "error"`) and records coordinator stage evidence (`coordinator:fixer-no-change` or `coordinator:fixer-policy`). The stage transitions to `blocked` status and publishes a durable `fix-blocked` presentation transition. These synthetic findings, blocker evidence, and blocked stage states survive detached resume as durable control-flow evidence, invalidating any stale preceding fix authorizations or auto-fix decisions so the blocker must be explicitly resolved. In the TUI, the active fixing glyph is shown only while the fixer is actively executing (`status === "active"`), while the fixer role heading is retained during the blocked decision wait. On startup or resume, the interactive Rail TUI reconstructs its activity model directly from persisted presentation snapshots without re-emitting plain-status output. The default maximum is three automated fix rounds, configurable via `--max-fix-rounds`. When the fix-round limit is reached with actionable findings remaining, the coordinator opens an exhaustion decision gate; resolving it with `fix` grants one further round and re-opens the gate if findings remain.

For worker stages, an `ask-user` finding or fix exhaustion opens an Orca decision gate offering `approve`, `fix [ids][: guidance]`, `skip`, and `stop`. The coordinator-owned `ci` stage is the exception: its gate offers only `fix` and `stop`, and `fix` resumes monitoring rather than dispatching a fixer (see [ADR-0016](adr/0016-ci-stage-monitoring-and-merge-settlement.md)). Unknown resolutions, and resolutions selecting an option the gate never offered, fail closed. Resolving with `fix` without IDs targets all actionable findings for repair. When explicit fix IDs are selected (`fix [id1, id2]`), only the targeted occurrences remain open for the fixer, while unselected open findings are approved immediately for that candidate. Those exact approved occurrences are filtered out of actionable control flow by `reconcileReportWithPreservedDispositions` (suppressing matching re-reported findings as `no-op`), so unselected findings remain approved across re-analysis and resume without opening an additional gate; operators must not mistake omission from a fix selection for deferring a decision. However, because finding dispositions are candidate-bound, candidate changes (such as commits produced by the fixer or rerunning a stage on an altered candidate commit) invalidate candidate-bound approvals, requiring fresh exact-evidence evaluation and gates if findings persist on the new candidate. Gate-response deliveries are processed completely before their batch acknowledgement, so multiple decisions delivered together are not discarded; acknowledgement failure aborts rather than replaying already-applied decisions. An in-flight worker question opens a distinct relay gate offering `reply` and `stop`, separate from finding, CI, and resume decisions. The gate carries the worker's question text and accepts only `reply: <actual answer>` or `stop`; any other resolution fails the stage, and the answer itself must carry the guidance because separate status messages are not forwarded. `reply` sends the exact answer to the worker's original question message on the same dispatch, so the worker continues without being restarted; `stop` tells the worker the human declined and stops the run. Responses and lifecycle messages continue to be processed through the active worker inbox while the relay is pending, so a completion that arrives with a reply still pending settles the question and completes the stage normally. A human may instead answer the durable question directly with `orca orchestration reply`, which never touches the relay gate; the coordinator observes that the dispatch no longer requests input and settles its own wait, while an unreadable dispatch projection stays a wait rather than closing a question that is still open. An unanswered question waits indefinitely: the worker's execution and inactivity deadlines are suspended while the relay is pending and restored when it settles. A reply to a dispatch that completion already closed (`dispatch_inactive`) is treated as neither failure nor success — the coordinator reconciles it against the actual lifecycle delivery — while any other reply error fails the stage. Every stage-scoped decision gate (finding, fix exhaustion, `ci`, and guardrail recovery) is recorded in `gate_audit` before the coordinator blocks, so a run interrupted mid-gate still carries the durable event. Relay gates and durable resume gates are not stage-scoped decisions: they are created against their Orca task and tracked only in Orca lifecycle state and the coordinator's in-flight wait, receive no `gate_audit` row, and so a relayed answer is never recorded as a candidate-bound waiver or approval. `approve` and `skip` complete the stage with unresolved findings and are recorded in `gate_audit` and bound into the attestation as a waiver on that stage's final evidence entry.

Checker and fixer prompts for Review, Test, Document, and Lint receive a bounded chronological history of recorded decisions from earlier steps and earlier runs on the same repository branch. A decline is derived as the complement of the stored selected IDs, so an explicit empty array preserves the difference between "the human declined every finding" and "no decision was recorded". Recorded decisions supersede conflicting intent wording, but the history is advisory and fail-open: malformed or unavailable history does not block a run, and an agent may raise a materially changed problem again.

Review checkers additionally receive same-run repair provenance, separate from decision history and fenced as untrusted evidence. For each earlier review fix round the coordinator reconstructs, from the durable `fix-completed` presentation snapshot and the review checkpoint recorded with it, the targeted finding IDs and their reported findings, the fixer summary, and the repair's input and output commits; this survives detached resume because it is read from the ledger rather than coordinator memory. The serialized history is bounded to 16 KiB: rounds are selected newest-first, an oversized round is omitted whole rather than truncated (the prompt then says rounds were omitted), and the retained rounds are presented oldest to newest. The reviewer is told to verify prior findings and fixer summaries against the cited commits before judging whether a repair exceeded the original finding; provenance is evidence, never authorization or proof. Other stages receive decision history only.

The adversarial review stage audits the diff for removed or weakened test assertions and relaxed linter/formatter/static-analysis rules, reconciling each against the declared intent. Relaxations the intent explicitly justifies are reported as informational `no-op` findings; anything else surfaces as a blocking `ask-user` finding with `id: unexplained-policy-relaxation` (`severity: error`) and opens a gate.

Review checker and fixer prompts also carry a remedy-scope contract. The checker classifies each finding by the scope of its smallest honest remedy rather than the defect's topic: `auto-fix` is reserved for mechanical repairs that stay within the authorized intent, including a source-proven fix at the shared boundary of sibling failures, while any remedy that extends the intent with new durable state, schema changes, background/retry/persistence machinery, or a subsystem, or that removes intentional behavior, is `ask-user`. On rereview the checker recommends returning an overbuilt round to its minimal fix as a single `ask-user` finding instead of a repair list that entrenches the excess. The fixer applies the same classification: selecting a finding does not authorize an undisclosed expansion, so a fixer that discovers the honest remedy exceeds scope reports the conflict in its summary rather than implementing it, and it removes intentional excess only after a human decision authorizes it. These rules are prompt guidance for the agents; the enforced coordinator guardrails remain the path and content guardrails described above, which apply regardless of what the prompt says.

Human decision gates have no coordinator-imposed deadline, and the pipeline has no total-run timeout. Explicit role timeouts bound individual worker attempts only; when one expires, the active worker operation is the single cleanup owner that aborts its in-flight run-mailbox wait, shell startup delay, readiness polling, or ACP subprocess, closes terminals, removes child worktrees, and waits for the entire owning operation, including recovery anchoring and strict cleanup, before finalizing the failed attempt. Worker inactivity uses one clock reset by terminal output or an authenticated heartbeat; when the terminal watchdog ends an attempt, the coordinator aborts and awaits the losing orchestration poll before cleanup. Receipt-producing terminal/worktree creation, authenticated dispatch, and native or supervised `worker-start` are allowed to settle so the coordinator can parse their receipts and remove resources created at the deadline instead of orphaning them. A timed-out worker receipt with no terminal still requires strict dispatch abandonment and removal of every known worktree before the attempt settles. Fresh candidates do not advance to a fallback unless worker abandonment, terminal closure, and owned-worktree removal all succeed. ACP attempts check the timeout fence before and after worktree setup so an expired attempt cannot launch paid agent work afterward. Unconfigured runs remain available overnight or through multi-hour review/fix loops.

## Evidence

Worker JSON reports, coordinator stage logs, and declared artifacts are confined to `~/.orca-no-mistakes/artifacts/<run-id>/`. The coordinator validates report shape and prevents report or artifact paths from escaping that directory. Nothing a stage produces is written inside the repository worktree.

Each round of the local stages and the `pr` drafting reviewer shares one 50 MB log at `~/.orca-no-mistakes/artifacts/<run-id>/<stage>_r<round>.log` (including `pr_r<round>.log`) across coordinator commands and worker attempts. It captures rebase output, worker provisioning and startup commands, terminal transcripts (including early and residual native startup output), test and lint commands, and ACP stdout/stderr as they arrive, so an interrupted coordinator retains the transcript already written. Terminal reads resume from a per-terminal cursor, record cursor gaps and truncation, and retain a final partial line without replaying completed output into a later round. Capturing is diagnostic and never fails the stage. An under-cap log keeps its existing physical bytes when reopened; trusted sidecar accounting is bound to the log's physical file identity and records both physical and cumulative original byte counts. Missing or mismatched accounting is reported as unknown instead of inferred. When new output would exceed the cap, the log is atomically rewritten as head, truncation marker, and tail; the marker reports dropped bytes, original bytes, and retained ranges when accounting is known, or marks them unknown otherwise. The coordinator-owned remote publication stage `push` has no stage log and writes only `push-r0.json`, while `pr` writes `pr-r<round>.json` as its remote evidence artifact alongside its drafting stage log. The coordinator-owned `ci` stage opens a registered stage log at `ci_r<round>.log` and appends every monitor status line (check state, base-tip re-arms, detected failures, merge, timeout) to it.

Each stage execution produces a `stage_evidence` row whose SHA-256 digest covers run ID, stage, round, candidate commit OID, base commit OID, worker identity, exit code, summary, and the SHA-256 digest of the stage's output artifact. `attestation verify` re-reads each retained stage artifact and recomputes both digests, requires every attested entry to still have its ledger row and vice versa, and cross-checks each row's recorded findings against the attested artifact, so editing a stage artifact, editing any bound field of the row, editing the recorded findings, or adding or deleting a row fails verification.

The completion manifest uses schema `version: "2.0.0"` (`PipelineCompletionAttestationManifest`). This is a data-format version, not a product release selector. It binds the frozen stage plan (`stagePlan`), terminal stage dispositions (`stageDispositions`), stage evidence (`stageEvidence`), publication route (`publicationRoute`), all attempt outcome digests (`attemptOutcomeDigests`, explicitly including the terminal passed attempt; only the pre-PR `pipelineEvidenceRoot` excludes that final digest), candidate publication receipt SHA-256 (`candidatePublicationReceiptSha256`), pull request binding receipt SHA-256 (`pullRequestBindingReceiptSha256`), custody (`custody`), assurance claims (`assuranceClaims`), and the pre-PR pipeline evidence root (`pipelineEvidenceRoot`). Its Merkle root covers the canonical JSON representation of the entire manifest, excluding `merkleRoot` itself, so all of these fields are tamper-evident.

Because the root covers the whole manifest, `attestation verify <manifest-file>` succeeds offline on a machine whose ledger has no record of the run, reporting that retained artifacts were not re-checked; a ledger that does hold the run must agree with the manifest exactly and additionally verifies gate waivers against durable gate audits. Each run also writes `manifest.json` beside its reports, recording `base_ref`, `base_ref_sha`, `local_bypass`, the effective policy configuration snapshot with resolved CLI overrides, and its `effective_policy_hash` (SHA-256 over key-sorted canonical JSON).

## Custody return

On success the coordinator evaluates the three-way containment proof between the submitted head (`C_sub`), the operator's branch head (`C_op`), and the terminal validated commit (`C_term`). It always anchors `refs/no-mistakes/recover/<run-id>` in the delivery repository at `C_term` first, before any head-advancing operation, so the gate worktree can be removed without stranding commits. When the pipeline ran directly in the operator's checkout, `C_op` is already `C_term` and no transfer is needed. In gate mode, a clean operator checkout still at `C_sub` is fast-forwarded to `C_term` by replaying the gate's commits. Every other case — divergent history, uncommitted operator changes, or a transfer that fails on the pipeline side — leaves the branch untouched; the recovery ref preserves the validated commits and the custody note names the ref plus the `git log` / `git rebase` commands to integrate it. Failed and cancelled runs likewise anchor their terminal gate head before teardown. Evidence is retained until explicit `prune`.

## Outcome

Before the manifest is assembled, the coordinator re-reads the run's durable evidence rows: if the latest round of any stage still records a finding that is not `no-op` and the attested entry carries no waiver naming a resolved gate decision recorded for that same stage and round, the run fails as unattestable. The completion attestation then binds the frozen plan and dispositions, stage evidence, route, both remote receipts, attempt-outcome history, custody, the pre-PR pipeline evidence root, and the complete Merkle root.

On success, an attached run prints the run ID, the nine core stages plus any configured command gates, lowercase `passed` verdict, custody note, policy provenance, and `completionAttestation`.

On failure the coordinator anchors the terminal gate head, appends the same recovery instructions to the terminal summary whenever the operator head differs from that anchored commit, throws, marks the run `failed` (or `cancelled` for a `stop` resolution), releases the lease, sets a nonzero exit status, and attempts to mark a direct worktree in review — except that when the interactive renderer reports a resumable error, the throw and nonzero exit are deferred through the durable resume-decision gate (see Orchestration): stop, a renderer failure revoking the wait, or a non-resumable error proceeds to them, and a resumed attempt that passes never throws. Orca-managed gate worktrees update their comments but never mutate their inherited workspace-status lane, so gate/reviewer/fixer children remain displayed under the worktree that spawned them even while their run state differs. If recovery anchoring fails, the gate and lease are retained instead of deleting the only reachable copy. A terminal outcome that cannot be delivered to the originating session over any notification transport likewise retains the gate worktree and terminal — including a passed run's — instead of cleaning them up, so `prune --stranded` can retry settlement and cleanup once the origin is reachable again. Worktree-status update failures are logged as warnings rather than changing the pipeline result.

Not yet implemented from the target architecture: CI auto-fix re-publication, trusted check-set completeness, guarded merge, delivered-tree verification, adoption of stranded `in-progress` remote runs or live interrupted workers, and canonical signatures over manifests. See ADRs 0003, 0004, 0006, 0007, and 0010.

Most subprocess commands time out after 120 seconds; worker orchestration uses longer waits. Gate polling inside the detached coordinator waits for human resolution or pipeline completion, while CLI commands return immediately to prevent agent deadlocks. `ORCA_CLI_COMMAND` overrides the Orca executable; the default is `orca` on macOS and `orca-ide` on Linux.

## Retained run compatibility

These rules apply to stored history; new runs use the pipeline described above.

- On first use, a repository transactionally imports its retained run graph and stored publication route from the archive returned by `legacyLedgerPath()`: `<ORCA_NO_MISTAKES_HOME>/ledger.db` when configured, otherwise `~/.orca-no-mistakes/ledger.db`. It then removes that repository's imported rows from the archive after commit. Other repositories remain untouched, and later openings check for unfinished imports. Migration fails closed while that repository has an `in-progress` run or lease in either ledger. Finish, cancel, or recover repository-ledger runs there; use `prune --stranded --repo <path>` for stranded archive resources. An interrupted source cleanup can be retried without replacing committed destination state.
- Attestation commands fall back to that archive only when no `--repo` was supplied and the current directory is not a Git repository.
- Frozen plans remain authoritative. Earlier eight-stage plans and attestations remain verifiable. Migrated six-stage local runs resume without GitHub initialization or credentials and return a local manifest under `attestation`; they do not acquire publication or CI stages. Historical managed-comment mutation intents remain readable.
- Local manifests use `version: "1.3.0"` (`PassedAttestationManifest`). Verification recomputes stage-evidence hashes, cross-checks the intent hash, and rebuilds a Merkle root over stage leaves and a header binding run ID, commit OIDs, policy digest, guardrail mode, intent hash, coordinator version, and creation time. Versions `1.0.0`, `1.1.0`, and `1.2.0` are rejected as unsupported. The historical type name does not imply the target `Passed` assurance claim.
- Test evidence recorded before the live-validation contract remains readable and verifiable without inventing live results.
