# Current Architecture

This document describes implemented behavior for Release 1 (Local Adversarial Validation Core). The ADRs under `docs/adr/` describe accepted target architecture; their `implementation` metadata states how much is current guarantee.

## Entry points

`orca-no-mistakes` supports four user-facing commands (plus the internal `gate` command used by the managed receive hook):

- `run` creates or reuses a deterministic direct admission. A newly pending admission launches the coordinator detached in an isolated child gate worktree and dedicated Orca terminal tab and returns `{"detached":true,"terminalHandle":"..."}`. An admission already being handled or accepted instead returns `{"admissionId":"...","replayed":true,"runId":"..."}` immediately without launching another coordinator; `runId` is `null` until a live launch binds its run, while a dead unbound launch is reclaimed first. If `--notify <handle>` is passed or `ORCA_TERMINAL_HANDLE` is set, the coordinator also notifies that terminal when a decision gate opens and notifies and wakes the originating session on terminal run outcomes (`passed`, `failed`, or `cancelled`). The internal `--attached` flag runs synchronously inside the spawned terminal tab; unless `--no-tui` is passed, the detached launcher injects `--tui` so the attached coordinator renders the interactive Run TUI by default, falling back to plain status on terminals that do not support it, while `--no-tui` renders each newly committed presentation snapshot as one bounded semantic stderr line and leaves stdout for the final structured result.
- `init` idempotently installs a repository-scoped bare gate at `<git-common-dir>/orca-no-mistakes/gate.git`, pins its own hooks path, advertises push options, and wires the managed `orca-no-mistakes` remote. Its `pre-receive` path accepts exactly one non-delete feature-ref update plus one canonical `no-mistakes.intent=<base64url>` option, validates the proposed commit in Git's quarantine, records or reuses a deterministic admission in the repository ledger, and launches a detached coordinator with receive state and pipes removed from its environment. The coordinator waits for the exact permanent ref, anchors that OID under `refs/orca-no-mistakes/heads/<run-id>` with a Git CAS transaction, and launches the existing isolated gate-worktree pipeline. During pipeline initialization, the domain run is created and bound to the admission, the branch lease is acquired, recovery context is registered, and only then is the admission marked accepted. Direct `run` admissions use the same ledger boundary and identity. A same-head push with no unfinished matching admission is a no-event, while a matching pending or launched admission is consulted and re-engaged; a same-head accepted admission is also a no-event, but an accepted admission that reaches the admission replay path returns its bound run.
- `attestation export|verify` writes a portable v1.3 local evidence manifest, or checks one against its own digests and — when this ledger holds the run — against the stored record and retained evidence. This schema predates the version 2 pipeline completion attestation. Both commands accept `--repo <path>` to name the repository ledger; without it they use the current directory and fall back to the legacy archive when that is not a Git repository, while passing `--repo` fails closed instead.
- `prune [--before <date>] [--repo <path>]` deletes completed runs (cascading checkpoints, evidence, gate audit rows, attestations, and the run's frozen plan and other Release 2 facts) plus their artifact directories; `prune --stranded [--repo <path>]` instead reaps dead gate and direct-run resources and rejects `--before`. `--repo` selects every run whose recorded root is that path or nested under it. The ledger row is deleted before its artifacts, because the delete re-checks the lease and can refuse a run that was leased again since selection; a failed removal therefore orphans a directory rather than stripping the evidence of a run that survived. It never deletes refs: preserved commits outlive the pruned run. Nothing else deletes evidence: there is no TTL or count-based eviction. For `prune` without `--stranded`, a run is retained when it still holds a branch lease, when its repository root is unavailable and `--repo` does not name that exact root (the exact-root assertion applies only to this case), or when any of its recovery refs — `refs/no-mistakes/recover/<run-id>`, the `-fixer-<stage>-<round>` children anchored per fixer round, and `refs/no-mistakes/recover-generations/<run-id>/<generation>` — is not an ancestor of its branch, base, or `origin/<base>`. A generation ref preserves the prior resume generation's tip, so it retains a completed run until that commit merges; the run becomes prune-eligible after containment is proven. A container ref that no longer resolves, such as a feature branch deleted after its merge, is skipped rather than treated as an inspection failure; any other Git failure aborts the prune instead of deleting evidence on a guess. Containment is proven outside the delete transaction and is not fenced against a concurrent run rewriting the same branch: because prune never deletes refs, the commits of a run pruned in that window stay reachable at their recovery ref, and only its row and logs are lost.

Before deleting a completed run, `prune` deletes every `submission_admissions` row bound to it. An identical later submission is therefore admitted again instead of replaying the pruned run.

Stranded recovery also handles direct attached Force stops. Their marker records the exact HEAD and owned worker state; recovery preserves that commit, reaps those workers, atomically settles an in-progress run cancelled and releases its lease, then removes only the marker, never the operator checkout or branch. If the run already reached `passed` or `failed`, recovery verifies the recorded commit is already preserved and leaves that terminal status unchanged.

New runs require an explicit single-line `--intent`; `--resume <run-id>` instead reopens a failed run with its stored intent. The runner requires a clean, committed, named feature branch, rejects the detected default branch, verifies an `origin` remote, and optionally checks an expected `--head` SHA. It fetches and rebases onto the selected base before validation continues.

## Domain ledger

Each repository's identity and provenance state lives in SQLite at `<git-common-dir>/orca-no-mistakes/ledger.sqlite` (WAL mode, foreign keys on), created via `node:sqlite`. On first use, a repository transactionally imports its retained run graph and stored publication route from the legacy `~/.orca-no-mistakes/ledger.db` compatibility archive when present, then removes that repository's migrated runs from the legacy archive once the import commits (a move, not a copy — other repositories' rows stay, and later openings re-check for stragglers); the import fails closed while any run for that repository is still in-progress or holds a lease in either ledger — a repository-ledger run must be finished, cancelled, or recovered there, while the legacy side recovers through `prune --stranded --repo <path>`. Every run freezes its stage plan (position, stage id, requirement) into `stage_plan_entries` in the same transaction as its `runs` row. The ten Release 2 fact tables — `stage_plan_entries`, `stage_dispositions`, `publication_routes`, `publication_baselines`, `run_attempts`, `attempt_outcomes`, `remote_observations`, `mutation_intents`, `remote_receipts`, `auto_fix_mode_events` — are write-once: UPDATEs abort unconditionally, and DELETEs abort while the run's own row still exists, so those rows leave only through the cascade when `prune` deletes the run. The default Release 1 flow populates the frozen plan, Auto-fix mode events, stored publication-route snapshot, and the per-attempt custody facts — one `run_attempts` row per attempt (initial and resumed) plus an `attempt_outcomes` row settled atomically with run settlement for passed, failed, and gate-stop-cancelled attempts (orderly Cancel and Force-stop or stranded-marker recovery settle the run cancelled without a per-attempt outcome row); focused publication additionally records the baseline, observations, mutation intent, receipt, evidence, and checkpoint. Twenty-four tables:

- `runs` — one row per run with submission commit OID, base branch/OID, intent + intent hash, trusted-policy hash, and terminal status (`in-progress`, `passed`, `failed`, `cancelled`); resumed attempts reuse the same row (`run_attempts` holds one row per attempt).
- `submission_admissions` — one deterministic submission identity per direct or gate ingress, carrying repository/ref/OID/intent identity, lifecycle status, optional launcher PID, and later run and accepted-OID binding. An accepted binding persists until its run is pruned; removing both allows an identical later submission to be admitted again.
- `pending_admission_leases` — one exclusive unfinished-admission lease per repository ref, preventing competing pending or launched submissions until acceptance, failure, or supersession releases it.
- `repository_migrations`, `repository_migration_imports` — markers for the first-use import: whether each legacy archive was imported (or recorded absent) for a repository, and which repository roots still owe an import. The documented migration itself depends on these markers and on `stage_plan_entries`.
- `repository_publication_routes` — the durable, repository-scoped publication route: one mutable row per repository keyed by the canonical Git toplevel, holding the forge host, stable repository/node/fork-network-root identifiers, owner and branch coordinates, the authenticated actor identity, its credential source (a label, never a secret), and the backend identity. Unlike the write-once per-run Release 2 facts it does not belong to a run: it is upserted in place, refuses a fingerprint change while in-progress runs still depend on the stored route, and every run snapshots it into its immutable per-run `publication_routes` fact at start.
- `stage_plan_entries` — the run's frozen stage plan, one row per stage with position, stage id, and requirement (`required`, `optional`, `disabled`); written atomically with the `runs` row, with six stages by default, and re-derived for legacy runs that predate it.
- `stage_dispositions` — one terminal disposition per plan stage (`satisfied`, `failed`, `skipped`, `waived`, `disabled`), bound to its plan entry and optionally to an evidence digest.
- `publication_routes`, `publication_baselines` — Release 2 remote-delivery facts: a run's route fingerprint with forge host and owner/branch coordinates, and its authoritative head-commit baseline (including the proven absence of one) bound to the canonical credential-free head-repository identity used at admission.
- `run_attempts`, `attempt_outcomes` — per-attempt custody facts populated by the default flow as well as focused publication: which coordinator/actor identity started each attempt under which generation token, and its terminal outcome (verdict, stopping fact, reason, candidate commit, custody and receipt digests, resume eligibility) stored with a SHA-256 digest over its canonical JSON.
- `remote_observations`, `mutation_intents`, `remote_receipts` — Release 2 remote-stage facts: hash-bound observations of remote state, intended remote mutations (candidate publication, pull request, managed comment), and the resulting receipts bound to the authoritative post-observation.
- `auto_fix_mode_events` — the run's immutable Auto-fix mode history: one append-only row per mode change with the enabled flag, source (`initial` at run creation from `auto_fix.enabled`, or `operator` for a Run TUI toggle), and timestamp; resume restores the latest recorded mode for the run.
- `branch_leases` — one exclusive semantic lease per `(repo_root, branch)` with a monotonically increasing generation token and heartbeat timestamp. A second run on a leased branch fails closed; `--force-lease` reclaims it. The lease heartbeat is checked before every stage and each fix round; losing the lease aborts the run. The lease is released when the run passes or fails.
- `lease_generations` — per-repository counter minting the monotonically increasing lease generation tokens.
- `resume_claims` — one claim per resumed run binding the run to its resume generation token.
- `stage_checkpoints` — every completed stage and fixer round records its input and output commit OIDs (each fixer must commit a distinct change). Detached resume reconstructs the isolated gate worktree at the newest checkpoint output while the initiating checkout remains at the original submission commit for automatic custody transfer. When a resumed generation rewrites lineage, `refs/no-mistakes/recover-generations/<run-id>/<generation>` preserves the previous generation's tip.
- `stage_evidence` — one row per stage execution binding stage id, round, candidate/base commit OIDs, worker identity, exit code, summary, findings, artifact path, the SHA-256 artifact digest, and the SHA-256 evidence digest. Indexed by run and by `(run, stage, round)`.
- `gate_audit` — every human gate, written when the gate opens with its kind (`exhaustion` or `finding`) and updated on resolution with the raw resolution, parsed decision, guidance, and selected finding IDs. Approve, skip, and stop store an explicit empty ID array, while an unresolved or invalid resolution keeps the field null. An unresolved gate stays `pending` with a null `resolved_at`.
- `presentation_snapshots` — append-only immutable projections of run attempts, mode, stage, round, finding counts, gates, errors, cancellation, and terminal outcomes. Settlement, checkpoint, and passed-terminal snapshots commit in the same transaction as their domain milestones; finding and gate snapshots follow their durable ledger rows, while start and round transitions are durable presentation events themselves. Resume loads the latest projection without replaying completed transitions. Transient elapsed time, cursor state, pane state, activity previews, and raw worker output are never stored.
- `passed_attestations` — one row per passed run keyed by run ID, holding the manifest JSON and Merkle root; lookups by candidate commit OID return the most recent attestation.

Set `ORCA_NO_MISTAKES_HOME` to relocate artifacts and the legacy migration-source archive (used by tests and sandboxes). It does not relocate repository ledgers.

## Orchestration

The coordinator creates one Orca Run and an ordered six-task DAG:

`intent -> rebase -> review -> test -> document -> lint`

A resumed coordinator creates a new Orca orchestration run for only the remaining suffix of this DAG while retaining the original domain run ID, artifact directory, evidence history, and attestation identity. Detached launch reconstructs the isolated gate worktree at the selected durable checkpoint and leaves the clean initiating checkout at the original submission commit so successful custody transfer can advance it automatically. The coordinator atomically reopens the failed ledger row and reacquires its branch lease, restores prior evidence and resolved approvals, replays a recorded `fix` decision that was interrupted before its fixer ran, and starts at the first incomplete stage. Commit-bound validation evidence is rerun when its candidate no longer matches the checkpoint HEAD.

The Run TUI adds a same-process resume path distinct from detached `--resume`. When a failed attempt settles with at least one checkpoint and its error is a resumable worker-stage execution failure — excluding intent/rebase stage errors, worker-cleanup failures, and post-mutation custody errors — the coordinator first drains the attempt's registered workers, then settles the failed attempt with its outcome and waits for the operator. `R` reacquires the resume claim and branch lease under a new generation token, starts a new attempt under the same domain run and the same Orca orchestration run, and continues from the durable checkpoint; `C` leaves the run stopped for a later detached `--resume`. A setup failure of the resumed attempt fails closed: the run settles failed with the resume claim cleared. When the interactive renderer is unavailable (plain-status fallback), the resumable error simply stops the run instead of waiting, and a renderer failure while that wait is open revokes it — the run settles failed with its original error — so detached `--resume` remains the recovery path in both cases.

`intent` records the supplied objective behind `<untrusted_instruction>` framing. `rebase` is a coordinator-run Git operation; the other stages are worker evaluations returning structured reports. The default six-stage plan executes no remote push, PR creation, or CI reconciliation.

The focused `scripts/publication.ts` API admits a custom plan whose final stage is `push`. Admission binds the canonical credential-free head-repository identity and authoritative fully qualified head-ref baseline; equivalent HTTPS and SSH spellings remain usable only when mandatory stable repository ID and node ID resolution identifies that same stored repository. Publication rejects Git URL rewrite configuration, requires the current generation-fenced branch lease, verifies each satisfied local stage's retained evidence artifact, and requires a contiguous terminal checkpoint chain. It then either records a no-op, explicitly reconciles an already-present exact candidate, or runs `git push --porcelain` with an explicit fully qualified refspec and `--force-with-lease=<ref>:<expected>`. Every attempted write is followed by an authoritative `ls-remote` read and another stable repository identity check; only an exact candidate match settles the append-only receipt, evidence, and push checkpoint. This API remains outside the default coordinator DAG.

Gate, CLI-worker, and ACP-worker creation explicitly reasserts the parent relationship after Orca returns the creation receipt, so an intermittently dropped create-time lineage record does not leave controllers or workers detached in the workspace hierarchy.

Reviewers run as fresh workers in disposable child worktrees. A compatible fixer terminal and child worktree are retained across fix rounds, with each committed repair applied back to the coordinator's isolated gate worktree; changing the primary configured fixer, observing that its worktree no longer matches the pre-round head, finding uncommitted changes, or failing to acknowledge retained-worker completion releases it before launching a fresh session. Another round enters through Orca's supervised `worker-start --terminal` path, which verifies that a recognized agent process still owns the terminal before delivering the authenticated task; a terminal that returned to its shell is released and retried through the fresh configured chain even when its stale title still names the old harness. If a retained terminal fails before accepting another round, the coordinator releases it and retries the full configured chain in fresh child worktrees. Retained fixers are released before a human gate opens. Every successful fixer round must leave a clean worktree and create a new commit. A fixer that reports no applicable change is cleaned up, recorded as evidence, and routed to the human gate so the operator can approve or skip a false finding or explicitly retry it.

The new commit must also change the pre-round tree. Empty commits are treated as no-change outcomes and follow the same cleanup, evidence, and human-gate path.

Fixer prompts restrict edits to implementation source and new regression tests (or the narrower document-stage scope). The coordinator binds policy inspection, custody transfer, and post-transfer HEAD verification to the same exact fixer commit OID, rejecting a worker or concurrent writer that substitutes a later commit after validation. Ordinary fixer commits must descend from the pre-round head. Rebase conflicts are never agent-fixed: the coordinator records the exact upstream OID from the same fetch/rebase attempt, pauses with only `fix` (retry after human resolution) or `stop`, and reruns the rebase stage when requested. In `strict` guardrail mode it rejects changes to tests present at the pre-round head, validation command/configuration files (including test-runner selection), and its executable entrypoint before applying a fixer commit. In `advisory` guardrail mode, protected-path and assertion changes proceed to custody while being recorded as guardrail violations. Coordinator source that entrypoint imports is code under review and stays fixable. Documentation under `docs/prompts/` remains ordinary document-stage content. A protected-path commit rejected in `strict` mode is cleaned up, recorded as stage evidence, and routed to an indefinite human gate with the complete structured stage report preserved rather than terminating the run.

This deliberately includes mechanical test/lint edits to an existing test file because the coordinator cannot prove that a file-level rewrite preserved its assertions. The path-level guard covers dedicated test files, including Perl `t/*.t`, Terraform `*.tftest.hcl`, Gherkin `features/*.feature` plus conventional `features/support/**` and `features/environment.py` support code at any repository depth, Bats `*.bats`, `specs/` and `__specs__/` directories, prefix-style `testFoo` and `TestFoo` names, C++ `*_unittest` files, snapshot assertions under `__snapshots__/` or `*.snap`, fixture/golden data under conventional `testdata`, `fixtures`, `__fixtures__`, or `golden` directories, Cypress/Playwright-style `*.cy.*` and `*.e2e.*` files, and pytest `conftest.py`. For ordinary implementation paths, the coordinator compares committed blob contents directly, independent of Git attributes and textconv. A pre-round source file containing a direct/chained test registration or an assertion-framework import anywhere in the source is immutable to fixers, covering control-flow-prefixed registrations and chained skip/only changes without language-specific parsing; documentation extensions (`.adoc`, `.md`, `.mdx`, `.rst`) are exempt from this whole-file freeze and instead receive the same statement-level assertion-unit and skip-marker protection as a merely-asserting file. A file that merely asserts is protected at statement level instead: each assertion, together with its multiline continuations or its doctest expected output, must survive the change unaltered, so unrelated edits to the same file remain fixable. Any changed pre-round path referenced by a protected manifest, CI workflow, or runner/build configuration is also protected; references resolve from both the repository root and the referring manifest's directory. A referenced local action protects its complete tracked implementation tree, while unreferenced files with similar names remain editable. Custody updates the operator worktree only while detached and moves its named branch through an exact compare-and-swap, preserving concurrent branch advances. A timeout before or during custody transfer restores the pre-round head; once transfer finishes within the deadline, coordinator verification and cleanup finish under their normal command bounds. Final certification remains fail-closed until the retained fixer terminal and worktree are released.

Validation references normalize optional trailing directory separators and resolve each CI step's `working-directory` or a shell command's `cd` together with that same command path, including newline-separated shell blocks, so separate steps cannot cross-match unrelated files with the same basename. Non-YAML policy sources such as Jenkinsfiles are inspected as complete shell blocks so directory context survives intervening setup commands. Referenced local actions protect nested action implementations throughout every enclosing action tree. A workflow `uses: ./` protects the root action manifest and descendants of directory entrypoints referenced by that manifest, without turning unrelated repository paths into policy. Implicit Bazel and Gradle policy files such as `.bazelrc` and `gradle.properties`, plus Gradle and Maven wrapper scripts, properties, and implementation files, are protected without requiring textual references.

A successful fallback fixer remains compatible while the exact configured candidate chain and order stay unchanged. Common GitHub, Forgejo, GitLab, CircleCI, Jenkins, Azure Pipelines, Buildkite, Bitbucket, Travis, and AppVeyor CI configuration, complete local GitHub/Forgejo action implementation trees, CMake and Bazel build/test entrypoints including `CMakePresets.json` and `CMakeUserPresets.json`, Meson's implicit `meson.build`, `meson.options`, and `meson_options.txt`, Maven and Gradle build policy including `.mvn/maven.config` and `settings.gradle(.kts)`, Go module/workspace manifests, PHPUnit runner configuration, TSLint configuration, dependency lockfiles, and any `conftest.py` are protected validation policy and cannot be changed by a fixer commit.

Clojure's canonical `project.clj`, `deps.edn`, and `build.boot` manifests are protected implicit validation policy. Validation-entrypoint closure also includes newly added paths when protected pre-round policy already names them, so a fixer cannot satisfy a missing check with a passing no-op.

Dedicated test-path protection also recognizes `.Tests`, `.UnitTests`, and `.IntegrationTests` project directories, hyphenated `foo-test` and non-document `test-foo` names, and Pascal/camel-case `Test(s)` or `Spec(s)` filename suffixes. While a human gate is open, the coordinator inspects and acknowledges the complete Orca delivery, applying authenticated gate responses and warning about unrelated messages rather than blocking or discarding the batch silently.

Every rebase attempt records the upstream OID fetched by that attempt, including conflicts, hook failures, and failures without unmerged paths; only a clean rebase updates the accepted run base. Exact `snapshots/` and Jest `__mocks__/` directories are protected test data. npm's implicit `.npmrc`, Go Task's `Taskfile.yml`/`Taskfile.yaml` and `Taskfile.dist.yml`/`Taskfile.dist.yaml`, `GNUmakefile`, and `.justfile` are protected validation policy. Validation references recognize repository-root command substitutions such as `$(pwd)` and `$(git rev-parse --show-toplevel)`, POSIX environment variables, PowerShell `$env:NAME`, Windows cmd `%NAME%`, and workflow-expression prefixes.

Each stage and role resolves its own agent from the configuration tiers, and the launch adapter dispatches on the resolved harness:

- `cursor` launches through native `orca orchestration worker-start`, which receives the resolved model, effort, and timeout as flags. Fresh Claude, Codex, Antigravity, and Kimi workers create their authenticated dispatch first, then launch through a local terminal with a protected mode-0600 preamble artifact. Claude, Codex, and Antigravity receive a short artifact instruction at launch. Kimi starts its interactive TUI with managed `--auto`, waits for stable readiness, and then receives the artifact instruction through Orca's agent-prompt terminal transport. Immediate argument, authentication, terminal, or readiness failures remain preflight failures. Retained CLI sessions re-enter through supervised `worker-start --terminal`, which validates agent ownership and delivers the authenticated task. Codex reasoning effort maps to `model_reasoning_effort` and automation uses `--dangerously-bypass-approvals-and-sandbox`. This avoids native fresh-launch prompt stalls, empty initial TUIs, prompt-processing races, one-shot Kimi execution, and OS argument-size limits.
- Before a fresh Kimi TUI starts, the coordinator refuses worktrees containing project `.mcp.json` or `.kimi-code/mcp.json`, then writes Kimi's exact per-workspace trust record only for that worker path. The temporary record is removed immediately after readiness and authenticated task delivery, so every fresh launch rechecks the worktree and automatic trust cannot enable branch-controlled project MCP servers.
- Fresh terminal workers wait 20 seconds when the controller's default shell is fish, allowing hidden panes to finish fish's ten-second terminal-query timeout and settle at a writable prompt before the startup command is sent. `WORKER_SHELL_STARTUP_DELAY_MS` overrides this compatibility delay. `opencode`, `grok`, and `gemini` then dispatch instructions by injection. `agy` receives its authenticated preamble through a protected prompt file passed to `--prompt-interactive`; because that carrier is a managed option, AGY overrides may not contain an option terminator. Its adapter also provides custom readiness matching and automatic workspace trust configuration in `~/.gemini/antigravity-cli/settings.json`. Trust updates serialize behind an owner-identified lock, reclaim only locks owned by a proven-dead process, and fail closed after a bounded wait when ownership cannot be resolved safely. Mandatory unattended flags are emitted before every `agent_args_override`, so an option terminator cannot turn them into positional text; overrides may add non-reserved arguments but may not supply managed permission, approval, sandbox, profile, or prompt controls, and resolved effort is passed through the harness-specific knob. Startup output naming the harness binary itself as missing fails immediately as `binary-missing` instead of burning the readiness timeout. Terminal titles remain the primary readiness signal; Codex additionally accepts its active working indicator plus model/effort footer because hidden Codex panes can retain the worktree title while already processing the task. Before each attempt, the coordinator removes the assigned report file. A successful worker may omit `--report-path` only when it wrote that newly assigned file; supplied paths must equal the assigned path and still pass canonical artifact containment checks. Worker reports and ACP stdout are parsed with closed JSON fences preferred over unclosed tails; disagreeing candidates fail closed at every layer, including the last-resort bare-object fallback.
- An invalid or unreadable worker report receives up to two fresh contract-repair tasks using the same selected candidate rather than advancing the fallback chain. Before strict cleanup, fixer report failures attempt the round recovery ref; cleanup independently requires a dispatch-specific worker recovery ref before removing an owned worktree.
- Every non-retained fixer outcome uses strict cleanup. A retained fixer is also released strictly when a later stage fails. If report validation, policy inspection, custody, execution, or later-stage failure cannot also release the terminal/worktree, the cleanup failure is surfaced after recovery bookkeeping with the original failure preserved as its cause; certification and fallback remain blocked.
- Retained `worker-start` receipts are parsed before fallback decisions. A receipt that exposes a dispatch but is not ready is abandoned before the retained session is released or another candidate starts.
- Retained `worker-start` command bounds include the configured readiness deadline plus startup slack, so readiness settings above two minutes are not truncated by the generic subprocess timeout.
- Antigravity lock reclamation preserves the ownerless lock's pre-claim identity and age, so creating the reaper claim cannot make the stale lock appear new.
- Co-located Zig `test "..."` declarations and `std.testing.expect*` assertions are protected. Playwright `*-snapshots` baselines are treated as test assertions. ShellCheck's implicit `.shellcheckrc` and Pipenv's `Pipfile` are protected validation policy.
- Rust test attributes include namespaced async/proc-macro forms such as `#[tokio::test]` and `#[rstest]`; JUnit `@ParameterizedTest` and NUnit `[TestCase]` registrations are protected too. Canonical Scala, Swift, Zig, Composer, Ruby, .NET, Elixir, and Dart package/build manifests and their standard lockfiles are protected validation policy because their test targets may be discovered implicitly.
- Qualified C# registrations and assertions, including NUnit and MSTest namespace-qualified attributes plus `Assert.*` calls, make a pre-round implementation source immutable to fixers.
- Recognizable JavaScript assertions include Chai modifier/property chains such as `value.should.not.equal(...)` and destructured Node assertion calls when the source imports `node:assert`, including `ok`, `equal`, `deepEqual`, `match`, and strict variants.
- Robot Framework `.robot` suites and `.resource` keyword files are dedicated test assets. Any pre-round non-documentation source importing `node:assert` or `node:assert/strict` is immutable to fixers, so aliased assertion APIs cannot bypass protection.
- Python's discovered `test*.py` files are dedicated tests. Protected validation commands resolve quoted or unquoted `python -m package.module`, launcher flags and value-taking options such as `py -3 -m` and `python -X dev -m`, package `__main__.py` entrypoints, and conventional `src/` package layouts to the corresponding tracked Python module.

- Gradle `testFixtures` trees are protected test data. Maven `.mvn/jvm.config` and Coverage.py `.coveragerc` are protected implicit validation policy.

- Conventional `e2e/` trees are protected test data. Actionlint `actionlint.yaml` and SwiftLint `.swiftlint.yml`/`.swiftlint.yaml` are protected implicit validation policy.
- Catch2/doctest `TEST_CASE` registrations and `REQUIRE`/`CHECK` assertions are protected co-located validation, and `vitest.workspace.*` is protected runner policy.
- Cucumber `features/step_definitions/**` and Behave `features/steps/**` are protected test support trees. GoogleTest `TEST_F`, `TEST_P`, `TYPED_TEST`, and `TYPED_TEST_P` registrations make their source files immutable, while `pytest.toml`, `.pytest.toml`, and `vite.config.*` are protected validation policy.
- Validation-entrypoint closure indexes each policy source once and processes newly discovered policy sources incrementally. It still uses path and shell heuristics rather than parsing every build system, so unusual conventions can remain unrecognized. Advisory mode records detected guardrail violations without weakening custody checks.
- Every rebase conflict requires human resolution. The conflict report carries the immutable upstream OID fetched by that exact attempt; selecting `fix` reruns the coordinator rebase after the human resolves or otherwise updates the branch, while `stop` cancels the run. Clean rebases remain automatic.
- Nox's implicit `noxfile.py` runner configuration is protected validation policy.
- Central MSBuild policy files `Directory.Build.props`, `Directory.Build.targets`, and `Directory.Packages.props` are protected case-insensitively because projects import them implicitly.
- Jest image baselines under `__image_snapshots__/` are treated as test assertions alongside `__snapshots__/`, `*-snapshots`, and `*.snap` files.
- Executable sources under a singular `spec/` directory are protected while declarative specification artifacts such as `spec/openapi.yaml` remain editable.
- Validation references normalize environment/workflow-expression prefixes, optional trailing directory separators, and POSIX or Windows path separators before resolving the command target. Shell `cd` and `pushd` directory changes use the same normalization, including quoted `$ENV/...` and `${{ ... }}/...` paths. Local-action directory references may include a trailing separator.
- Shell-composed validation references track nested relative `cd`/`pushd` transitions and `popd`, retaining directory context through `&&`, `;`, newline-separated setup commands, and guarded `cd dir || exit ...; command` forms.
- PowerShell `Set-Location`/`Push-Location`/`Pop-Location` transitions, including `-Path` and `-LiteralPath`, participate in the same validation-command directory state.
- Validation-policy source traversal resolves standard extensionless JavaScript/TypeScript imports and directory `index` modules, so referenced assertion helpers inherit protection.

- Protected `tsconfig*.json` path aliases are resolved when a protected validation source imports the alias. Windows cmd `cd /d` transitions participate in composed-command resolution, and `pnpm-workspace.yaml` is protected implicit validation policy.

- TypeScript alias resolution accepts BOM-prefixed JSONC and supports `baseUrl` without a `paths` table. POSIX `cd --`, `cd -L`, and `cd -P` transitions participate in composed-command resolution. `*.golden` files are protected assertion data, and `lerna.json` is protected implicit workspace policy.
- Conventional `integration/`, `integration-test(s)`, and `integration_test(s)` trees are protected test paths. .NET solution manifests (`*.sln` and `*.slnx`) are protected validation policy.
- Maven Invoker `src/it/` trees are protected test paths, and Ant's implicit `build.xml` is protected validation policy. Every tracked descendant of a referenced non-root local action directory is protected, even when the action manifest does not name that descendant directly.
- Android/Gradle variant source sets such as `src/testDebug/` and `src/androidTestDebug/` are protected test trees alongside `src/androidTest/`, `src/commonTest/`, and other `*Test` source sets.
- Jest `<rootDir>` references, local Python imports from protected runners, and shell subshell directory scopes participate in transitive validation-entrypoint resolution. Directory changes made inside `( ... )` are restored before later outer commands are resolved.
- Jenkins `dir(...)` scopes, including nested scopes, participate in the same validation-entrypoint resolution without inheriting shell-local `cd` state from separate `sh` blocks.
- Python `from package import module` and relative `from . import module` statements protect the corresponding tracked validation modules.
- Yamllint's implicit `.yamllint`, `.yamllint.yml`, and `.yamllint.yaml` files, Oxlint's `.oxlintrc.json`, lint-staged's `.lintstagedrc*` and `lint-staged.config.*` files, and `.husky/` hook scripts are protected validation policy.
- A reviewer `worker_done` outcome of `failed` never completes a stage. The coordinator still reads and canonically validates the assigned, path-confined report for diagnostics, but the transport failure remains fatal even when that partial report contains actionable findings. Fixer workers retain strict successful-outcome handling.

- Co-located Vitest/Playwright `expect.soft(...)` and `expect.poll(...)` assertions are protected.
- Pre-round sources importing, value-re-exporting, or forwarding entire assertion modules containing `expect`, `assert`, or `should` from Jest, Vitest, Playwright, Chai, or the standalone `expect` package are validation-bearing even when those APIs are aliased; equivalent CommonJS property extraction and module forwarding are covered too. Type-only and unrelated framework imports remain editable.
- Codex `-c model=...` and `-c model_reasoning_effort=...` pins take precedence over mapped values, normalize whitespace around `=`, and must contain nonempty values. Worker waits ignore stale messages from prior sequential dispatches instead of failing the active worker.
- Worker waits ignore syntactically malformed or non-object metadata that cannot be attributed to the active dispatch; a valid active completion later in the same delivery still wins, while a delivery with no valid active message is acknowledged and polling continues.
- Known harness names are normalized case-insensitively before launch classification, managed safety flags, effort mapping, override lookup, and prompt-mode selection. Unknown custom executable names retain their original casing.
- `acp:<target>` harnesses run through the `acpx` runner (`acpx --format quiet --approve-all <target> exec --file -` with the prompt on stdin, so large prompts stay off argv and a failed write surfaces the child's stderr) and must return a JSON stage report; report-shaped candidates disambiguate extraction so thinking-model reasoning that quotes JSON cannot hide the payload.

Reviewer reports require canonical structured findings because they drive gates and fixer selection. Fixer reports use only their summary, tested commands, and declared artifacts; noncanonical fixer finding metadata is ignored because commit ancestry, protected-path policy, and exact-OID custody independently decide whether the repair may be applied.

Terminal-launched harnesses use per-harness readiness matchers; startup waits up to `WORKER_AGENT_READY_TIMEOUT_MS` milliseconds (default 60000) before the terminal and any allocated worktree are torn down. With no configuration the default remains one `opencode` worker per role on the agent's own default model; `--reviewer-model`, `--fixer-model`, and `--fixer-effort` override per role at the highest precedence.

## Validation policy

Two provenance rules bind every run. First, repository agent configuration is read from `.orca/no-mistakes.yaml` on the trusted base ref (`git show origin/<base>:.orca/no-mistakes.yaml`); an absent file resolves to an empty policy, and an unresolvable base ref fails the run. Second, the coordinator hashes its own script files as they exist at `origin/<base>` and records that digest in the ledger and attestation. Reviewer prompts frame repository content, diffs, and instructions as untrusted data; policy changes may only come from the coordinator prompt itself.

The extracted configuration supplies per-stage and per-role agent selection and is merged under the CLI flags. `--allow-local-config` reads the same path from the working tree instead, and `--config <path>` reads an explicit file that must exist. Either bypass marks the run uncertified: the Orca worktree status is prefixed `[uncertified: local config bypass]` and the artifacts manifest records `local_bypass`.

## Findings and gates

Findings are `auto-fix`, `ask-user`, or `no-op`; a report finding that omits `action` is conservatively defaulted to `ask-user` instead of failing the report, while an explicitly invalid action still fails it. Reports containing only actionable `auto-fix` findings enter the fix loop automatically only while the run's durable Auto-fix mode is enabled; with the mode disabled they open the finding gate instead. The mode is recorded at run creation from `auto_fix.enabled`, and every operator toggle from the Run TUI (`A`) appends an immutable `auto_fix_mode_events` row; a toggle affects only findings recorded after the change, and a resumed attempt inherits the latest recorded mode. Each recorded finding carries a `fixed`, `approved`, or `open` disposition, surfaced as per-finding counts by both renderers, and resume reconciles approved stages back into the presentation. The default maximum is three automated fix rounds, configurable via `--max-fix-rounds`. When the fix-round limit is reached with actionable findings remaining, the coordinator opens an exhaustion decision gate; resolving it with `fix` grants one further round and re-opens the gate if findings remain.

An `ask-user` finding or fix exhaustion opens an Orca decision gate offering `approve`, `fix [ids][: guidance]`, `skip`, and `stop`. Unknown resolutions, and resolutions selecting an option the gate never offered, fail closed. Gate-response deliveries are processed completely before their batch acknowledgement, so multiple decisions delivered together are not discarded; acknowledgement failure aborts rather than replaying already-applied decisions. Every gate is recorded in `gate_audit` before the coordinator blocks, so a run interrupted mid-gate still carries the durable event; `approve` and `skip` complete the stage with unresolved findings and are recorded in `gate_audit` and bound into the attestation as a waiver on that stage's final evidence entry.

Checker and fixer prompts for Review, Test, Document, and Lint receive a bounded chronological history of recorded decisions from earlier steps and earlier runs on the same repository branch. A decline is derived as the complement of the stored selected IDs, so an explicit empty array preserves the difference between "the human declined every finding" and "no decision was recorded". Recorded decisions supersede conflicting intent wording, but the history is advisory and fail-open: malformed or unavailable history does not block a run, and an agent may raise a materially changed problem again.

The adversarial review stage audits the diff for removed or weakened test assertions and relaxed linter/formatter/static-analysis rules, reconciling each against the declared intent. Relaxations the intent explicitly justifies are reported as informational `no-op` findings; anything else surfaces as a blocking `ask-user` finding with `id: unexplained-policy-relaxation` (`severity: error`) and opens a gate.

Human decision gates have no coordinator-imposed deadline, and the pipeline has no total-run timeout. Explicit role timeouts bound individual worker attempts only; when one expires, the active worker operation is the single cleanup owner that aborts its in-flight run-mailbox wait, shell startup delay, readiness polling, or ACP subprocess, closes terminals, removes child worktrees, and waits for the entire owning operation, including recovery anchoring and strict cleanup, before finalizing the failed attempt. Worker inactivity uses one clock reset by terminal output or an authenticated heartbeat; when the terminal watchdog ends an attempt, the coordinator aborts and awaits the losing orchestration poll before cleanup. Receipt-producing terminal/worktree creation, authenticated dispatch, and native or supervised `worker-start` are allowed to settle so the coordinator can parse their receipts and remove resources created at the deadline instead of orphaning them. A timed-out worker receipt with no terminal still requires strict dispatch abandonment and removal of every known worktree before the attempt settles. Fresh candidates do not advance to a fallback unless worker abandonment, terminal closure, and owned-worktree removal all succeed. ACP attempts check the timeout fence before and after worktree setup so an expired attempt cannot launch paid agent work afterward. Unconfigured runs remain available overnight or through multi-hour review/fix loops.

## Evidence

Worker JSON reports, coordinator stage logs, and declared artifacts are confined to `~/.orca-no-mistakes/artifacts/<run-id>/`. The coordinator validates report shape and prevents report or artifact paths from escaping that directory. Nothing a stage produces is written inside the repository worktree.

Each stage round shares one 50 MB log at `~/.orca-no-mistakes/artifacts/<run-id>/<stage>_r<round>.log` across coordinator commands and worker attempts. It captures rebase output, worker provisioning and startup commands, terminal transcripts (including early and residual native startup output), test and lint commands, and ACP stdout/stderr as they arrive, so an interrupted coordinator retains the transcript already written. Terminal reads resume from a per-terminal cursor, record cursor gaps and truncation, and retain a final partial line without replaying completed output into a later round. Capturing is diagnostic and never fails the stage. An under-cap log keeps its existing physical bytes when reopened; trusted sidecar accounting is bound to the log's physical file identity and records both physical and cumulative original byte counts. Missing or mismatched accounting is reported as unknown instead of inferred. When new output would exceed the cap, the log is atomically rewritten as head, truncation marker, and tail; the marker reports dropped bytes, original bytes, and retained ranges when accounting is known, or marks them unknown otherwise.

Each stage execution produces a `stage_evidence` row whose SHA-256 digest covers run ID, stage, round, candidate commit OID, base commit OID, worker identity, exit code, summary, and the SHA-256 digest of the stage's output artifact. `attestation verify` re-reads each retained artifact and recomputes both digests, requires every attested entry to still have its ledger row and vice versa, and cross-checks each row's recorded findings against the attested artifact, so editing a stage log, editing any bound field of the row, editing the recorded findings, or adding or deleting a row fails verification. The Merkle root covers a header leaf — run ID, both commit OIDs, the policy digest, the guardrail mode, the intent hash, coordinator version, and creation time — alongside the stage-evidence leaves, so those header fields cannot be rewritten on an otherwise intact manifest. The manifest version is `1.3.0`; `1.0.0` predates the run ID in the evidence preimage, `1.1.0` predates the header leaf, and `1.2.0` predates the guardrail mode, so all are rejected as unsupported versions rather than reported as tampering. Because the root covers the whole manifest, `attestation verify <manifest-file>` succeeds offline on a machine whose ledger has no record of the run, reporting that retained artifacts were not re-checked; a ledger that does hold the run must agree with the manifest exactly. Each run also writes `manifest.json` beside its reports, recording `base_ref`, `base_ref_sha`, `local_bypass`, the effective policy configuration snapshot with resolved CLI overrides, and its `effective_policy_hash` (SHA-256 over key-sorted canonical JSON).

## Custody return

On success the coordinator evaluates the three-way containment proof between the submitted head (`C_sub`), the operator's branch head (`C_op`), and the terminal validated commit (`C_term`). It always anchors `refs/no-mistakes/recover/<run-id>` in the delivery repository at `C_term` first, before any head-advancing operation, so the gate worktree can be removed without stranding commits. When the pipeline ran directly in the operator's checkout, `C_op` is already `C_term` and no transfer is needed. In gate mode, a clean operator checkout still at `C_sub` is fast-forwarded to `C_term` by replaying the gate's commits. Every other case — divergent history, uncommitted operator changes, or a transfer that fails on the pipeline side — leaves the branch untouched; the recovery ref preserves the validated commits and the custody note names the ref plus the `git log` / `git rebase` commands to integrate it. Failed and cancelled runs likewise anchor their terminal gate head before teardown. Evidence is retained until explicit `prune`.

## Outcome

Before the manifest is assembled, the coordinator re-reads the run's durable evidence rows: if the latest round of any stage still records a finding that is not `no-op` and the attested entry carries no waiver naming a resolved gate decision recorded for that same stage and round, the run fails as unattestable instead of producing its v1.3 local evidence manifest. The check reads the ledger rather than the stage loop's own bookkeeping, so it holds independently of that control flow.

An attached run prints `{"runId":...,"steps":[...],"attestation":{...}}` after completion; the attestation manifest carries the run ID, candidate/base commit OIDs, trusted-policy hash, intent + intent hash, ordered stage-evidence entries (including waivers), Merkle root, and coordinator version. On failure the coordinator anchors the terminal gate head, appends the same recovery instructions to the terminal summary whenever the operator head differs from that anchored commit, throws, marks the run `failed` (or `cancelled` for a `stop` resolution), releases the lease, sets a nonzero exit status, and attempts to mark the worktree in review — except that when the interactive renderer reports a resumable error, the throw and nonzero exit are deferred through the post-failure `R`/`C` resume wait (see Orchestration): `C`, a renderer failure revoking the wait, or a non-resumable error proceeds to them, and a resumed attempt that passes never throws. If recovery anchoring fails, the gate and lease are retained instead of deleting the only reachable copy. Worktree-status update failures are logged as warnings rather than changing the pipeline result.

Not yet implemented from the target architecture: automatic push/PR/CI stage orchestration, adoption of live interrupted workers, canonical signatures over manifests, forge-side delivery verification, and guarded merge transitions. See ADRs 0003, 0004, 0006, 0007, and 0010.

Most subprocess commands time out after 120 seconds; worker orchestration uses longer waits. Gate polling inside the detached coordinator waits for human resolution or pipeline completion, while CLI commands return immediately to prevent agent deadlocks. `ORCA_CLI_COMMAND` overrides the Orca executable; the default is `orca` on macOS and `orca-ide` on Linux.
