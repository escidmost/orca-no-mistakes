# Review evaluation

`./bin/orca-no-mistakes evaluation` captures fixed code-review cases, runs the
existing ACP review worker against them, and compares findings with explicitly
adjudicated issue labels. It requires Node 24+, Git, and, for real model calls,
an authenticated `acpx` installation. It does not need an Orca run or GitHub
publication initialization.

## What is reproducible

A case contains a self-contained `repository.bundle` with the exact candidate,
base and their reachable Git history, plus `case.json` containing the frozen
review prompt, intent, decision history, branch display name, coordinator source
digest, and source provenance. The input SHA-256 is the case ID. Bundle bytes have
a separate verified digest. Each capture writes to a staging directory and then
renames it into the corpus; an existing case is verified and reused. Source
references are retained separately so another source run does not change input
identity. Labels and replay results never change the captured inputs.

This reproduces **review inputs**, not deterministic model output. Reviewer config
requires an explicit `acp:<target>`, model, per-worker timeout, and an operator
description identifying the installed harness version and relevant settings.
The external provider, harness installation, authentication, home configuration,
and model service are not archived. Record changes to those in a new config's
`environment` value. A result records the selected config and its hash plus the
executing coordinator digest; it does not claim an independently verified model
identity. Prompts are replayed verbatim, not regenerated by the newer coordinator.

Capture operates on committed Git content, not dirty files or installed build
outputs. Shallow history, submodules and Git LFS pointers in the base/candidate
are rejected because their complete content is not retained by this workflow.
Diff context uses the existing review policy's 200,000-character limit; the full
Git objects remain available for inspection. No dependencies are installed.

Replay uses an independent temporary Git repository, detached at the captured
candidate, with no remote and no shared object store. It calls the existing
`CliOrca.startWorker` ACP path and `validateReport` for the review stage. It does
not invoke fixers, pipeline decisions, publication or source-ledger writes.
Changed checkout state or added remotes cause replay failure; disposable state is
removed afterward. This is state isolation, **not an OS security sandbox**: the
existing ACP adapter uses its normal permissions and inherits the environment
with Git repository/config overrides removed so they cannot redirect its checkout.
Use an appropriately isolated host for untrusted reviewers or repositories.

**Provider use:** local corpus storage does not make replay offline. Repository
code and the prompt can reach the selected model provider. Corpus bundles contain
reachable history, including files beyond the displayed diff; keep them private.
The existing ACP quiet transport exposes no token/usage receipt, so results record
`usage: null` with a reason, never a fabricated zero.

## Capture and seed

Use a private corpus outside the source checkout. By default it is
`~/.orca-no-mistakes/evaluation` (under `NO_MISTAKES_HOME` when overridden).

```bash
./bin/orca-no-mistakes evaluation capture --corpus /private/reviews \
  --repo /path/to/repo --base BASE_COMMIT --candidate CANDIDATE_COMMIT \
  --intent intent.txt --source 'ticket:ONM-101' --note 'Explicit review snapshot'
./bin/orca-no-mistakes evaluation list --corpus /private/reviews
```

`--intent` names a UTF-8 file. Capture prints the case ID. This is a **new review
snapshot**, even when the commits are historical: the supplied intent and current
coordinator policy become its declared inputs. It is not evidence of what a past
worker saw. Capturing another intent/prompt/coordinator produces another case.

The small explicit seed is `acceptance/review-corpus.json`: the real ONM-100
multiplication-defect candidate and its repaired candidate, pinned by full Git
IDs. Its positive issue cites the explicit authored correction in commit
`322473d7a5ee93dc5c3f5abcbd4da2ad25bc2686`. The repaired case is clean for that
known arithmetic defect, but its labels remain incomplete; no negative gold is
inferred from a repair, approval, skip or merged PR. The seed declares an
evaluation intent that asks reviewers to report the intentionally planted defect.

```bash
./bin/orca-no-mistakes evaluation seed --repo . --corpus /private/reviews \
  --manifest acceptance/review-corpus.json
```

Seed import trusts the operator-reviewed issue provenance in the manifest; it
does not authenticate the human author. It never infers labels from pipeline
outcomes. Keep the resulting case IDs for comparisons. Seed Git objects must be
present for the initial capture; afterward the retained bundles are sufficient.

To import an already frozen historical case:

```bash
./bin/orca-no-mistakes evaluation capture --corpus /private/reviews \
  --from /path/to/run-artifacts/review-cases --case CASE_ID
```

Import carries inputs and provenance, not labels/results. An old run with only
findings, decisions, checkpoints or a verdict lacks complete replay inputs.
Import fails with an incomplete-input explanation rather than substituting
current policy. Missing or corrupted bundles also fail closed.

## Replay two explicit configurations

Save a JSON config as `reviewer-a.json`, for example:

```json
{
  "harness": "acp:claude",
  "model": "your-explicit-provider-model-id",
  "timeout_ms": 600000,
  "environment": "acpx version and agent version; relevant user settings"
}
```

Create `reviewer-b.json` with the second explicit target/model/environment.
No implicit model, effort mapping, fallback reviewer or paid test call is used.

```bash
./bin/orca-no-mistakes evaluation replay --corpus /private/reviews \
  --case CASE_A --case CASE_B --config reviewer-a.json
./bin/orca-no-mistakes evaluation replay --corpus /private/reviews \
  --case CASE_A --case CASE_B --config reviewer-b.json
```

Selection is sorted and rejects duplicate or missing IDs. Without `--case`, the
CLI snapshots all currently retained IDs before starting; explicit IDs are best
for repeated comparisons. Each successful call prints a JSON result with case,
config and result IDs, validated candidate findings, elapsed worker/validation
time in milliseconds, and usage availability. Failed calls exit nonzero and do
not create a successful result. No timeout covers the full corpus or a human
decision; `timeout_ms` bounds one reviewer attempt.

## Adjudicate and compare

Gold has three separate concepts: confirmed case-local issues, candidate findings
explicitly mapped to an issue, and explicitly rejected findings. Everything else
is pending human judgment. Review the concrete claim before writing a label and
name the decision's source, not merely a PR merge or pipeline approval.

```bash
./bin/orca-no-mistakes evaluation adjudicate --corpus /private/reviews \
  --case CASE_A --result RESULT_ID --finding 0 \
  --issue total-multiplication --description 'Total must multiply price and quantity' \
  --source 'human:review-note-123' --note 'Verified total(2,3) gives 5 instead of 6'
./bin/orca-no-mistakes evaluation adjudicate --corpus /private/reviews \
  --case CASE_A --result RESULT_ID --finding 1 --reject \
  --source 'human:review-note-124' --note 'Claim is unreachable under the supported input contract'
```

Finding indexes are zero-based. Omit result/finding to record a known issue before
any replay. Reuse an existing issue ID and its same description when mapping
another finding to it. For the seed, use its existing issue ID/description rather
than creating a duplicate. Matching is an exact SHA-256 of validated finding
content, including ID, description, location, severity and action. Identical
findings share a judgment; differently worded findings need another explicit
mapping. There is no fuzzy match or automatic model judge.

Only a separate human completeness judgment may set `--complete`, with `--source`
and `--note`. Even then, an unmatched new finding stays pending. Label revisions
are retained and the latest label pointer is replaced atomically.

Create `selections.json` as an array of `{ "caseId": "…", "resultId": "…" }`, with
exactly one result per case/config and the same case set for each config:

```bash
./bin/orca-no-mistakes evaluation compare --corpus /private/reviews \
  --selections selections.json
```

The readable report includes config/model identity, case/result/gold IDs, latency,
issue counts and each finding's status. Known-issue recall is unique matched
confirmed issues divided by known confirmed issues. Judged-finding precision is
accepted findings divided by accepted plus human-rejected findings. Pending
findings are excluded from that precision denominator. No known issues or no
judged findings yields an undefined (`n/a`) metric, not perfect accuracy.
Incomplete gold means these are conditional measurements, not exhaustive recall
or false-positive rates. Multiple findings for one issue cannot increase issue
recall beyond one matched issue.

## Optional completion capture and retention

After using the explicit workflow, opt in through **user-global** config:

```yaml
evaluation:
  capture_on_completion: true
```

Default is false; a repository config cannot opt the user in. When enabled, the
coordinator creates a new evaluation snapshot before each review in the run's
`review-cases` directory. On successful completion it imports those cases into
the default corpus. It uses the shared review policy, a freshly pinned base and
candidate, the current decision history, a relative repository path and the ACP
delivery envelope. The resulting evaluation inputs are frozen, but this does not
claim a byte-identical reconstruction of the original worker session, ambient
harness state, or malformed-report retries. Capture/import failures emit a
warning and cannot change the pipeline verdict. No gold labels are generated.

Retention is manual. Bundles are self-contained, so source branch deletion,
source garbage collection or pruning a different case cannot remove objects
needed by a retained case. Replays and label revisions remain with their case.

```bash
./bin/orca-no-mistakes evaluation prune --corpus /private/reviews --case CASE_ID
```

This explicitly removes that case, its bundle, labels and results. It does not
delete source refs or objects. To bound storage, periodically list and prune cases
you no longer need; automatic capture has no hidden age eviction. Corpus writers
use a short-lived `.writer` directory lock. A concurrent writer fails rather than
stealing it. After a crash, verify no corpus writer remains before removing a
stale lock. Interrupted `.capture-*` or `.import-*` staging directories are not
selectable cases and may then be removed.

## Offline verification

`node --test tests/review-evaluation.test.ts` uses a disposable fixed Git corpus
and fake ACP executable: known defect, repaired/clean case, extra unmatched
finding, and incomplete historical inputs. It exercises capture, object retention,
two explicit configurations, isolation, scoring and completion import without
calling a paid model. The pipeline regression in `tests/orca-no-mistakes.test.ts`
also forces capture failure and asserts the successful verdict is preserved.

CI-miss auto-labeling is a later extension. This workflow does not infer it from
today's CI monitor, a repair commit without issue provenance, or a merge.
